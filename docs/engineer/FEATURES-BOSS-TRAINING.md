# Gameplay features: Boss Matches (Nioh3BossRematch) and Training (Nioh3Training)

**What this is.** A feature-by-feature engineering guide to the two gameplay ASI mods: `Nioh3BossRematch` (boss matches, the mod
menu, soul-core transformations, the boss logger) and `Nioh3Training` (practice sessions, arena swap, boss move controls, practice
stats, frame meter, style meter, player log).
**Who it is for.** An engineer who already reads C/C++ and x64 and needs to know what the player sees, which game functions and data
each feature uses, which ini keys control it, and where the known limits are.
**Truth source.** The current source tree (add-on 1.5.6). The public `mod/` copy is older (add-on 1.5.1); anything that exists only in the
current source is marked. Paths are repo-relative with no line numbers.

Related docs, not repeated here: [`../../README.md`](../../README.md) (install and feature list),
[`../../CONTRIBUTING.md`](../../CONTRIBUTING.md), [`../../PUBLIC_EXCLUSIONS.md`](../../PUBLIC_EXCLUSIONS.md),
[`../code-map.md`](../code-map.md), [`../subsystems/mission-logic.md`](../subsystems/mission-logic.md) (mission scripts),
[`../../research/boss-exe-strings.md`](../../research/boss-exe-strings.md), [`../../symbols/README.md`](../../symbols/README.md).
The source tree also keeps working notes under `notes/` (for example `notes/rematch-all-bosses.md`, `notes/auto-arena.md`,
`notes/training-mode-design.md`, `notes/soulcore-pick.md`); only some of them are mirrored in the public `research/` folder.

## 1. Architecture in one page

| Piece | Role | Key files |
|---|---|---|
| `Nioh3BossRematch.asi` | Boss Match engine, mod menu model, boss logger, soul-core forms, keep-gear and loot-clear helpers | `mod/Nioh3BossRematch/src/rematch.cpp` (engine plus menu text), `bosslog.cpp` (loggers and soul-core forms), `hooks.cpp`, `main.cpp`, `ui.cpp`, `remote.cpp` |
| `Nioh3Training.asi` | In-place arena swap, summoned bosses, sessions, move/stagger/aggro control, practice stats, meters | `mod/Nioh3Training/src/training.c` (one translation unit that `#include`s the `*.h` files) |
| `Nioh3EngineFix.asi` | Draws the mod menu in its DX12 overlay when present; hosts some rows (Time of day, Weather, Player log) | `mod/Nioh3EngineFix/src/menu.cpp`, bridge `mod/rematch_menu_bridge.h` |

How they talk:

- BossRematch finds Training with `GetModuleHandle("Nioh3Training.asi")` and calls its C exports by name with `GetProcAddress`
  (`TrainingExport(...)` in `rematch.cpp`). A missing export disables only the rows that need it, so a new BossRematch with an old
  Training degrades instead of failing. Training does the reverse for two BossRematch exports: `Nioh3BossRematch_ClearDroppedLoot` and
  `Nioh3BossRematch_LessonNote`.
- All Training exports are declared `N3T_API` (`__declspec(dllexport)`) in `training.c` and the `*_game.h` files. Names are
  `Nioh3Training_<Verb>`; for example `FightNow`, `FightNowChr`, `SummonSlot`, `SessionMode`, `ReturnHome`, `PracticeStatGet/Set`,
  `BossVitalsGet/Set`, `StyleGet/Set`, `SoulCoreEquip`, `PlayerLogGet/Set`, `KeepGear`.
- Every game call and every game-memory write runs on the **game thread** (the per-frame pump: the call-site retarget in `hooks.cpp`).
  The menu thread and the pipe only post request words.
- Patch resilience: BossRematch resolves each site by script-native name or by a wildcard byte pattern (`mod/Nioh3BossRematch/sites.json`,
  `src/sites_gen.h`, generated by `mod/Nioh3BossRematch/tools/derive_sites.py`). Training uses RVA tables (`rvas.json`,
  `src/rvas_gen.h`, `mod/Nioh3Training/tools/gen_rvas.py`) wrapped in `Grva()`, which returns 0 on an unknown build. Each feature group
  switches itself off with the reason in the log. Neither mod refuses to load because one group failed.
- Solo/offline only. Gates are re-checked on the game thread right before each call. No story flag is ever written.
- Builds: BossRematch with MSVC (`mod/Nioh3BossRematch/build.bat`, soul-core code compiled with `/DBR_SOULCORE=1`), Training with zig's
  clang (`mod/Nioh3Training/build.sh`; `-fasync-exceptions` so `__try` guards on raw reads work).
- Logs: `Nioh3BossRematch.log` and `Nioh3Training.log` next to the ASIs.
- A dev command file `Nioh3Training.cmd` (one command per line, header of `training.c` lists them: `spawn`, `arena`, `warp`, `bbm`, `train`,
  `retry`, ...) and a local pipe `\\.\pipe\nioh3bossrematch` (`[Remote] Pipe = 1`; commands `ping status scan row start abort open scroll
  fight shrine again leave exit cover peek scrollctl trainscroll` plus soul-core dev commands) exist for test tooling.

## 2. Boss Match (rematch)

### 2.1 What the player sees

The mod menu (F7, or hold View + D-pad Up for 1 s; `[Menu] Hotkey`, `PadGesture`, `Overlay`) has three hosted tabs: **Boss Matches**,
**Practice** and **Player** (LB/RB switches tab). With `Nioh3EngineFix` loaded the menu is drawn by its overlay; otherwise `ui.cpp`
draws a topmost layered GDI window and reads the pad through the game's own `XInputGetState` import (the previous pointer is always
called). While the menu is open the pad is masked from the game.

The Boss Matches list is built from the catalogue (section 2.2). Rows can be filtered with the **List** row: All, Multi, one stop per
era, Dojos, "Not recently confirmed", Scrolls, Favorites (`rcore::BuildListCycle` in `src/rematch_core.h`; computed from the loaded rows,
no hand-kept list). Right on a row marks a favorite, Left unmarks. Opening a boss shows:

| Row | Meaning |
|---|---|
| **Fight now - ...** | Native mission load of the boss's mission, then the player is put in the arena so the game's own trigger starts the fight (2.5). |
| **Shrine before the boss** | Same mission, start point only (you appear at the start point beside the boss arena). Absent when the mission already starts at the fight. |
| **Train in this arena (no boss, no waves)** | The arena trip without the boss start (2.7). |
| **Train here** | A Training session with that boss where you stand (Training's `train`). |
| **Staged start: Full climb / Final wave** | Only for staged fights (2.10). |
| **Replay mission** | The game's own Battle Scroll replay (R-a) or a direct request (R-b); shown with `[Rematch] ShowUnverified = 1`. |

Rows that cannot start show the reason in the footer ("Arena unavailable: ...", "No route: ..."). A row can carry a catalogue
`warning` that is shown in orange ("Known bug"). Status words on a row: Fight now, Train here, Unavailable, Lesson, Known bug.

### 2.2 The catalogue: `Nioh3BossRematch_bosses.tsv`

Generated by `tools/rematch_catalog.py` (source tree only; not yet in the public copy) from the game's own data, never edited by hand.
`--check` fails if the committed TSV differs from a rebuild. The add-on parses it with `rcore::ParseCatalogue`, **by header name**, ASCII
only, up to 512 rows. Current content: 121 rows (R 58, D 10, H 3, E0 20, X 30).

| Column(s) | Meaning |
|---|---|
| `id`, `name`, `mission_name`, `region`, `boss` | Row key (for example `R1CBC`: route letter plus mission id in hex), display names, era. |
| `route` | `R`, `H`, `D`, `E0`, `X` (2.3). |
| `replay_mission_id`, `story_mission`, `hidden`, `defeat_kind`, `defeat_id` | The mission the game replays and how its defeat is checked. |
| `emaki_byte`, `emaki_key_u32`, `emaki_index` | Picture Scroll record plumbing (E0 rows). |
| `placement_id`, `region_byte` | Expected boss placement id (as seen at `Character::Create`) and the world byte the boss stands in. |
| `verified`, `seen`, `confirmed` | Evidence flags. `confirmed` is the date of recorded live entry evidence; the menu's "Not recently confirmed" stop uses it. `Nioh3BossRematch_verified.tsv` (written by `tools/rematch/verify_all.ps1`) overrides `verified` at run time. |
| `stage_mission`, `warp_x/y/z/yaw`, `box_id`, `fight_kind`, `fight_dist_m`, `fight_conf` | The Fight-now **start point**: the mission start-point record chosen next to the boss, its spawn transform, the boss-area box, how it was picked and how sure (2.4). `-` = not offered. |
| `arena_x/y/z/yaw`, `arena_box`, `arena_src`, `arena_conf`, `arena_boxgeo` | A point just inside the arena trigger box, the box id, where it came from, confidence, and the box geometry (centre, yaw, size) so the run-time can test "inside". |
| `gate_id`, `gate_kind`, `boss_pos` | The id the boss start function waits on (`Function::WaitWarpStart`) and whether it is a `door` gadget or a `box`; the boss position. |
| `lesson`, `fight_signal`, `wave_groups`, `clear_x/y/z` | Script kind from a script scan: `boss` (the script calls `Mission::BossBattleMode`) or `waves` (it calls `Character::IsDeathGroupEnemy` and never `BossBattleMode`), the wave group ids and the clear gadget position. |
| `mission_class` | The game's own mission class (for example `dojo-way`, `main`, `named-linked-battle`, `hidden-wave-stage`); the Dojos filter is built from it. |
| `summon_chr`, `wake_step`, `warning`, `reason` | Field-only X rows: the enemy record's `Load::Character` key; E0 rows: the wave-wake warp offset measured in test runs; a known live problem; the reason an X row has no route. |

The same generator also writes `notes/rematch-all-bosses.csv` (one row per boss name, with unverified items and reasons).

### 2.3 Routes, and what "no route" means

| Route | Source of the mission | How it starts |
|---|---|---|
| `R` (58 rows) | A listable Battle Scroll mission (record flags `+0x40` has none of `1`, `0x40`, `0x4000`). | **R-a**: the game's replay list via `MenuOpenMissionReplay(0, 0, 6)`. **R-b** (`[Rematch] DirectStart = 1`, and always for Fight now): `MissionRequestById(id, slot, startPoint, params)`, the same call the shrine replay confirm makes. |
| `H` (3) | One of the data-hidden duels (flag `0x4000`). | R-b directly (the request does not look at the list flag), or R-a with `[Rematch] HiddenDuels = 1` (bit cleared, restored on close). |
| `D` (10) | Shipped mission records the replay list never shows (master duels and "hidden-wave" stages). | R-b on the unlisted record; refused unless the mission reads cleared on this journey. |
| `E0` (20) | The 20 Picture Scroll records of the generic scroll mission (`0xCC96`). Waves, not named bosses. | Scroll entry (2.11). |
| `X` (30) | **No route.** | Listed greyed with the `reason` column; never started. |

An `X` row means the tool could prove no safe way in. The reasons in the data: the boss exists only in an open-field region mission
(19 rows, `field only`), the name matches no character id or mission record (`no data`), the character has no boss record
(`+0x9C` bit 4) in any shipped mission, or the script leaves the boss frozen. Field-only rows that have a picked enemy record carry
`summon_chr`; the menu then offers "Teleport to this boss's field spawn and summon it beside you" (`Row::OpenWorld`). With
`[Rematch] ShowAll = 0` X rows and unbeaten bosses are hidden.

### 2.4 Universal rules (nothing per boss is hardcoded)

Project rule: no boss, mission, move or map lists in code. Everything that looks per-boss is derived from game data by a generator and
is checkable by re-running it. The rules live in `tools/rematch_catalog.py` (the C port used at run time is in section 3.1).

**`pick_fight_start(fi, mission, placement, facts)`** chooses the start point (mission record `+0x6C` table, 0xA4-byte records:
`+0` id, `+8` flags, `+0xC` kind, `+0x40` spawn x y z yaw) nearest the boss placement (enemy table `+0x54`, 0x138-byte records).
In order:

1. A mission with exactly one start point: that point ("mission start"; high confidence within 30 m, medium within 80 m, else low).
2. Start points with flag `0x200` (post-boss or script retry point) are never used.
3. Candidates are sorted by "same floor as the boss first" (more than 5 m of height difference sorts last), then by distance.
4. Flag `0x40` within 40 m: the boss retry point class, high confidence.
5. A plain spawn point (kind 0) or gadget point (kind 908) at 8 to 40 m, or a shrine (906, 907, 909) at 8 to 60 m: medium.
6. Anything else within 120 m (including points closer than 8 m): low. Farther: not offered.
7. No boss placement (dojo and wave missions): the single mission start, measured to the clear gadget, else the enter box.

**`pick_gate(fi, mission, placement)`** returns the gate id the boss start function waits on (`WaitWarpStart`): the only gate of the
mission, or, with several, the one whose function creates the boss placement. `gate_kind` says whether that id is a door gadget or a
trigger box.

**`pick_arena(...)`** finds the arena trigger: the `PlacementBox` the mission script tests with `Player::IsEnter*Box*`,
`Function::Wait_Invade*` or `Function::Loop_*EnterPlacementBox*` (the id pushed right before the call), with `BOSS` in its name and not
`BGM/JUKE/ITEM/GUEST/INV/SILENCE/CLEAR/VOICE/TALK/NOKATANA`, at most 40 m from the boss; otherwise a `BOSS` area box of the table
(lower confidence). The point is 60 percent of the way from the box centre toward the start point, on the boss's floor, facing the boss.
A geometric exception exists for a doorway trigger that lies between start point and boss (the start-point half is outside the arena);
it is a rule on box geometry (boss outside the box, cosine below -0.9, halves more than 3 m apart), not a per-boss entry. When a Fight now
log recorded where the game itself put the player at `BossBattleMode` start, `notes/arena-fightstart.csv` (from `tools/harvest_fightstart.py`)
overrides the point for the Training-only offer.

Generated run-time headers follow the same principle (each starts "Generated by tools/..."; no row lists in code):
`src/native_entry_gates_gen.h` (mission, placement, gate: a literal `WaitWarpStart` linked to the creating function),
`src/native_entry_waves_gen.h` (staged wave chains), `src/native_branch_entrances_gen.h` (missions whose script tests a mission flag
and calls `BossBattleMode` with a different placement), and in Training `native_entry_boxes_gen.h`, `native_entry_sequences_gen.h`,
`native_no_boss_mode_gen.h`, `fallback_rosters_gen.h`. All of these are.

### 2.5 Fight now, step by step (`rematch.cpp`)

1. The menu posts `kReqFight`; the game-thread pump takes it. Gates: solo/offline, not loading, not paused, no fight running, nothing
   active, spawn and scroll-map recovery resolved, `AttemptStartGate()`.
2. Clear check, `ClearedNow(mission)`: reads the clear database (`MissionClearedGetSlot`). An uncleared mission is allowed only for a
   Boss Match (or `[Rematch] IgnoreProgress = 1`) and only if the **clear guard** is installed: `Mission::SetMissionClearFlag` is vetoed
   by `InstallVeto` in `hooks.cpp` while that trip runs, so no clear, unlock or first-clear reward is written. The clear byte is read at
   arm and at disarm and logged; it must stay 0. The active unbeaten story mission is refused.
3. The request: `MissionRequestById(mission, slot byte, startPoint, {101, 1000000, 10100, 0, 0, 0})` with `alignas(16)` params. The third
   argument is request `+0xC`, the start point (the value Continue passes for the saved retry point). Nothing is patched, so nothing
   has to be restored; a death reload returns to the same start point because the mission state's retry point is that start point.
4. `FightNowSpawn = 1` (default): the start point's warp-point record is rewritten **in memory only** (spawn x y z yaw at `+0x40..+0x4F`,
   arrival-camera bit `+8` bit 4 cleared) so the game places the player and centres stage streaming at the arena point from the first
   frame. The record is restored when the Fight now ends. If it does not take, the old path runs: load at the start point, then warp
   after landing (the tail of `Player::SetPos`: `SetPos` with yaw, actor sync, position notify, scene position, stage path).
5. After landing, the player is in the trigger box and the game's script starts the fight (`BossBattleMode`). `FightSettleMs` is the
   wait after the load ends before the player counts as landed; `FightNudgeMs` warps the player 4 m in front of the boss if no fight
   began and the boss is out of duel range.
6. **Verification** (`SelfTest`, pipe `fight`): armed, warped, then PASS (a `BossBattleMode` after the first warp) or FAIL (none within
   8 s). For rows whose mission already starts at the fight (`atFight`) no warp is needed.
7. The Return page (a clear-gadget "Return" object, Training's gate zone) offers "Return to where I was" and "Fight again".
   `FightAgainDirect = 1` asks for the boss mission at once; 0 goes home first.

Cross-world and in-place variants live in Training (section 3.2). The Teleport rows ("Teleport to arena (normal loading)") use a native
load; `TeleportFastLoad = 1` ends each load screen once the target world's stage is ready and requests the boss gate sooner.

### 2.6 Arena door and gate opening

Many boss scripts wait in `Function::WaitWarpStart(gate)` until a player interacts with the fog door. The add-on does what the door does:
`RightsRequest(slot, key)` (the call behind `StartWarpByGadgetRights` / `StartWarp`). It hooks the check core
(`RightsCheckHook`, called from `Online::IsExclusiveRightsValue`), copies the 16-byte key the boss start polls for the catalogue `gate_id`,
and requests it once the boss start is waiting. This moves nothing, so it also stays on when Training owns the destination. For
Training-owned trips only a **script-observed** gate counts (`NativeEntryGateFind(mission, placement)` from the generated header), because
generated `WaitWarpStart` dependencies include box gates and indirect or wave creators. A `box` gate is not a door: stepping into the
box starts `BossBattleMode` on its own (about 2.7 s after arrival), so an arena-only trip cannot hold it (2.7).

### 2.7 "Train in this arena" and "Train here"

- **Train in this arena** = the row's arena with no boss and no waves; Training's menu then summons bosses as usual. Decided from row data
  by `rcore::ArenaTrainRouteFor`: `kAtNative` (Fight now load plus arena warp with the boss gate never requested; only where the boss
  start waits on a script gate or a door gadget, and the row has a catalogue arena point) or `kAtScroll` (a Picture Scroll arena with
  `Emaki::RequestWaveBattle` skipped). Refusal texts say why: the boss starts with the mission (nothing to hold), it starts on a trigger
  box, or no known spot inside the arena. A refused request clears both halves of the pick (BossRematch's row pick and Training's
  `SetArenaOnlyNext`) so the next normal Fight now fights.
- **Train here** = `Nioh3Training_TrainHere`: a Practice session with the boss beside the player, no load, any world (3.2).

### 2.9 Dojos

Dojo rows are the missions whose class is `dojo-way` (9 rows). The script, not a list, decides the class
(`rematch_catalog._script_is_lesson`, column `fight_signal`):

- **Duel dojos**: the teacher flow waits until the player is in a small start box or the teacher takes damage, then calls
  `Mission::BossBattleMode(teacher)`. They behave like boss rows (single mission start point, no gate).
- **Lesson dojos** (`fight_signal = waves`, footer "Lesson: defeat the waves, then follow the white dot and hold RB"): the script keeps the
  teacher dormant until `Character::IsDeathGroupEnemy` is true for the current lesson group. `HkLesson` hooks that native; the first check
  on a waves row is treated as the fight start and calls `Nioh3Training_WavesFight(1)`; an unmatched `BossBattleModeEnd` is the win
  (`rcore::WavesFightStarts`, `WavesUnmatchedEndWins`). The hook never kills, warps or writes mission state. The lesson-end
  white dot (`UI::SetCompassDestination`) is logged for test tooling only.
- Sandbox missions (tutorial, dojo) strip and re-give items and gear; section 4.1 handles that. A covered dojo entry is refused while
  you are still in another dojo.

### 2.10 Staged fights

Some boss missions are chains of wave stations before the boss (for example a fight where four box-triggered waves each set the boss
to a fixed fraction of health). `native_entry_waves_gen.h` records, per mission, the station count `n`, each station's wave id, box and
centre, and the boss health fraction (`hp_thou`, thousandths) written before the last station. The **Staged start** row picks:
*Full climb* (every generated wave) or *Final wave* (request only the last wave and optionally set that boss's health to the chain's
pre-final fraction; `src/staged_start.h`). Session-only, no mission-flag or save writes.

### 2.11 Picture Scrolls (E0 rows)

The 20 Picture Scroll records are listed under the **Scrolls** filter and as "Waves" rows (`"<area>: <n> waves, <toughest enemy>"`).
They are not boss fights and arm no boss bar. Fight now on a scroll row starts that record through the game's own scroll entry
(`EmakiMissionRequest`, owned scroll item as carrier), without using up a scroll (`rematch.cpp` header, `ExecEmaki`). The header describes
the default as a key-seed search that does not rewrite the Emaki byte-to-record map; the older redirect (`rcore::MapRedirect` with CRC
snapshot and restore) is kept and can be turned back on by the dev command `scrollctl`. After the load one shared warp walks the live
record point, then x and z offsets of 600 and 1500, until the wave state reads 3 (`rcore::WaveNudgeAt`; `wake_step` caches the offset that
worked). A wave-state 1 afterwards ends the fight. "Train in this arena" on a scroll skips `Emaki::RequestWaveBattle` through a wave guard
(`g_waveVetoOk`). "Train here" does not pick a scroll.

## 3. Training mode (`Nioh3Training.asi`)

### 3.1 Data files

| File | Content and use |
|---|---|
| `mod/Nioh3Training/Nioh3Training_arenas.tsv` | Arena table (234 rows). Columns: mission, start point, world, boss character id, boss placement id, player x y z yaw, boss x y z, `kind` (`arena` inside the trigger, `start` the Fight-now start point, `field` open-world spawn, `summon` roster only), id, name, optional cell lists (arena cells admitted during a cross-world switch and the placeable whitelist). Header carries a game-data fingerprint. Generated by `tools/auto_arena.py` (or `gen_arena_table.py`). |
| `Nioh3Training_bgm.tsv` | Mission to boss BGM hash (first `Sound::PlayBossBGM` in the boss script), so a summoned boss plays its music. |
| `Nioh3Training_actionsets.tsv` | One row per boss action file: file hash, character, row count and the action-object hashes. Used to bind a live boss to its action file (3.3). `tools/gen_actionsets.py`. |
| `Nioh3Training_action_records.tsv` | Columns `boss, action_id, motion, anim_hash, hit_count, damage_per_hit, zero_power`: facts extracted from the game archive (11,477 rows). The loader (`action_records.h`) is atomic: a malformed or oversized table leaves the previous table untouched. |
| `style/rank_atlas.png` | Style-meter sprite atlas (5). |

**Auto arena.** At startup (`[ArenaSwap] AutoArena = 1`) `src/arena_scan.h` re-derives the same arena rows directly from the game's data files
(archive folder, no exe addresses, about 0.2 s): the LFM id table, the mission table (0x198-byte records), per mission the enemy tables,
the `PlacementBox` table (0xA0 B), the start-point table and the script. Any boss mission or boss character missing from the TSV gets a row
and a summon-roster entry (names become `Boss <chr>` until a TSV names them). It is a C port of `tools/n3lfm.py`, `tools/auto_arena.py` and
the `pick_*` rules above, and `mod/Nioh3Training/tests/arena_scan_test.c` checks it row for row against the Python generator. If the known
file paths move after a patch, the tables are found again by structure. The TSV is a cache plus an override (hand-measured cell lists are
carried by row id).

### 3.2 Entering a practice fight

Two families of entry, both reached from the same menu:

- **Boss Match Fight now**: the native mission load described in 2.5. The ini notes in `Nioh3Training.ini` state the current rule: fog gate,
  arena intro, boss BGM, clear flags and rewards belong to the boss's mission script, so a mission Fight now always uses the native
  mission load plus arena auto-entry. The older in-place paths (`NativeEnter`, `NativeMissions`) are retired.
- **Practice sessions** (no mission): `Train here`, **Training Bosses**, **Summon Boss**. A boss is created next to the player in
  whatever map is loaded (any world): `Load::Character` for the model, then `CreateDynamic`, with `SetAwareFlg` called `AwareDelayMs`
  later so passive bosses notice you, a perception-list fix, the boss HP gauge (`ShowBossGauge`) and boss BGM. Native mission boss mode
  is replicated for HUD and music with a native replica of `Mission::BossBattleMode`/`End`. Summoned bosses get letters (Boss A, B, ...
  unlimited), each with its own page and per-slot state (`SummonSlot`, `SlotChr`, `GetSlotStance`, ...).
- **Arena swap** (`[ArenaSwap]`): "Fight now for a boss whose arena is in the world you stand in skips the mission load" (the player is
  warped into the arena, the boss spawned live), and `CrossWorld = 1` does a `World::WarpOtherWorld` request then the swap. The long list
  of `CrossWorld*` keys tunes that switch (early swap, prewarm, preload, area-object skip, cell-admission blocking, placeable skip,
  near-arena-only). Most are default 0 because they trade pop-in for speed. `HookFightNow = 0` is deliberate: hooking
  `MissionRequestById` made the menu report an uncertain native request. `BossGraceAfterCoverMs` holds the boss AI off until the screen
  is really visible; `BossHoldMaxMs` caps the hold.

Session rules (`[Summon]`): `PlayerNoDeath`, `SessionNoDeath` (default 1: dying in a session is always an in-place round reset, never
the game's death and shrine load), `PlayerCantDie` (infinite health, default 1; 0 means HP at the floor counts as beaten and you respawn
in the arena after `BeatenRespawnMs`), `SummonNoDeath`, `RespawnOnWinMs`, `AutoRetryOnDeath` (always on now), `SummonPassiveMs` (3000: a
menu-summoned boss stays passive this long), `BossLoot`, `BodyFade*`, `KillFade*`, `DeathBlowRequired`, `CutsceneOnKill`,
`FinisherKillTimeoutMs`.
A retry (`TrainRetry`) also calls `Nioh3BossRematch_ClearDroppedLoot` (4.2).

Fallback rosters. A mission with several bosses in sequence cannot be summoned as one actor. `fallback_rosters_gen.h` lists, from the
catalogue and same-mission enemy index, the characters in catalogue order; Training tracks kills per roster member and advances with the
native script phase when one reports. Rows the generator cannot disambiguate have `count 0` and are not fallback-capable.

### 3.3 Boss moves: auto moves, action sets, action records

What the player sees: on a Boss page, move groups (**1 hit, 2 hits ... 12 or more hits, Grabs, Unblockable, 0 hits, Other attacks (hits
unknown), Attacks, Unnamed attacks, Twitches, Ki break, Movement and reactions, Unsorted, Sequences**; `src/move_cats.h`). Each move row
toggles allowed or blocked (Left blocks, Right allows), and A or Right makes the boss **repeat** it with a configurable delay
(`RepeatGapMs`, 0 to 10000 ms). A Sequence row repeats a whole chain of "next action on finish" links; the game plays the links natively.
Move rows carry a type (Attack, Grab, Unblockable, Wind-up, Link, Twitch, Movement, Idle) and a hit count; "Show non-attack moves" reveals
twitches.

How it works:

1. **Binding** (`autobind.h`, `autobind_game.h`; `[Debug] AutoBind`, default 1): the boss's current action object gives `[obj+0x20]`, its
   336-byte action row in the loaded action file. The file's rows are contiguous; walking them yields the file's action-object hash set,
   matched against every set in `Nioh3Training_actionsets.tsv` by best Jaccard. Only struct offsets are used: no boss names, no fixed ids.
2. **Auto moves** (`auto_moves.h`, `auto_moves_game.h`; `[Debug] AutoMoves`, default 1): when a boss spawns, its loaded action data is
   read from memory, rebuilt into a file image, and parsed. File layout: `u32 n = 16`, then 16 (offset, size) sub-tables; sub-table 0 =
   header and per-action packed hitbox lists, 1 = 336-byte action rows, 2 = 192-byte hitbox rows. Per action it yields id, motion, the
   next action on finish (`+0xE0`), attack block, the GreatAttack (unblockable) flag, the hit count (hit windows of the action's own
   hitbox rows) and a kind (`A` attack, `M` movement, `I` idle). The same rules produce `mod/boss_moves.h`, `boss_move_facts.h` and
   `boss_sequences.h` offline (`tools/gen_boss_moves.py`, `gen_boss_move_facts.py`, `gen_boss_sequences.py`), so the runtime result can be
   compared one to one with the generated headers.
3. **Action records** (`action_records.h`): the TSV above is joined on action id plus motion plus animation hash and **replaces** the
   run-time window estimate of hit count and damage per hit (`ArApply`) before the catalogue is published. Conflicting joins stay unknown.
   Without the table the log says so and hits come from hitbox rows only.
4. `[Debug] HandMoves` (default 1) seeds the catalogue from the hand-checked tables in `mod/` as a fallback; 0 means nothing by hand.
5. Forcing a move: the select hook at the boss AI's pick transition vetoes or replaces the pick (`move_toggle.h`, `MvRepeatPick`); the
   repeat starts a move with the game's forced transition `66C4A8(ctrl, id, 0, 0.0)`. In the **Stand still** stance the boss AI is off
   (`idle_hold.h`, `slot_hold.h`), so `drill.h` starts the repeated move itself whenever the boss is back in idle and the gap has passed;
   if a forced move never starts three times in a row, the AI is switched on for the drill only.
6. A Boss Match ignores saved Training vetoes, repeats and the stance timer (generation counter `g_bm_gen`), but a change made from the menu
   during the match applies.

Stance rows: **Fight normally** (AI on), **Stand still** (AI off), a timed switch slider (1 to 10 s) between CPU and idle, `SummonPassiveMs`.

### 3.4 Ki break and stagger

The `[Summon]` `KiBreak*` keys implement the Ki-break behaviour of a practice boss: `KiBreakNoFinisher` (no grapple finisher on a
Ki-broken boss; gold Ki bar and an HP-0 window), `KiBreakBareFix` (a "bare" break, bit `0x3A` without stagger bits, would show a crouch
with no animation, so it is cancelled back), `KiBreakActFix` (swap the bare break to the boss's learned **good** hit reaction action).
The good action is learned from a real stagger the boss plays natively. For bosses that never play one, `src/auto_stagger.h` learns the
boss's **hit-reaction action** from its own behaviour: an action id that, outside any Ki break, almost only starts right after a hit
landed (at least `AST_MIN_HITS` hit runs, at least 75 percent of its runs being hit runs; the pick maximises hit runs times capped average
duration; idle ids and the boss's known bad ids never qualify). No per-boss table. The gold Ki bar overrides the HUD layout's vertex
colours (`GoldKiBar`, `GoldKiRGB`, `GoldKiLearn`, `GoldKiColors`).
The Practice stats rows add `OneHitKiBreak`, `HoldKiBreak` (+ `HoldKiBreakV2`, a Ki-pool hold) and `KiFloorDepth` (4.3).

### 3.5 Boss aggro

`src/aggro.h`. **Boss aggro on me** (`[Training] BossAggro`, default 0) every 250 ms, for sessions bosses whose AI is on: `SetAwareFlg`
every 2 s; make the player the current perception target if it is in the list but not current (the native insert tail); add accumulated hate
(`SetInitAccumulatedHate` body) every 2 s; and, beyond `AggroRangeCm` (500 = 5 m), put the AI state into a chase filter that lets only
locomotion picks through, so the boss walks up with its own AI and then the drill or gap logic resumes. Hate alone does not make a passive
boss approach; the range rule is what does. `AggroFace`, `AggroWalkTimeoutMs`, `BossRefillDelayMs` tune it.
**Reset boss position** returns the session boss to its round-1 spawn (summoned bosses to where they appeared) with the game's own
non-player warp, facing the player.

### 3.6 Boss vitals

Per boss page (Boss A, B, ...; `boss_vitals.h`, `boss_vitals_game.h`, menu in `boss_vitals_menu.h`): live HP and Ki read-out, **Boss infinite
health**, **Boss infinite Ki** (optional so Ki breaks still happen; a boss already Ki-broken is left alone until the break ends),
**Set boss HP %** (1 to 100) and **Set boss Ki %** (0 to 100; 0 means Ki 0.5, one hit from a break, because a plain 0 write is the bare break
that `KiBreakBareFix` cancels), **Refill boss**. State is per slot and session-only (defaults off). A new Training boss in a Practice
session starts with infinite health and Ki; a Boss Match boss does not. Infinite health refills only after `BossRefillDelayMs` without a
drop, and never kills meanwhile.

### 3.8 Frame meter, freeze, negative-Ki meter

- **Frame meter** (`frame_meter*.h`, `frame_probe*.h`; `FrameMeter`, `FrameMeterStyle` 0 row or 1 ring, `FrameMeterRingSize`,
  `FrameMeterLegend`, `FrameMeterReadout`, `FrameMeterKi`, `FrameMeterIFrames`, `FrameMeterY`, per-legend-group `FrameMeterKey*`): a
  fighting-game style boss frame bar drawn in its own click-through layered window. One run is one boss action; cells are 60 fps frames of
  a pausable clock. Cells are pending, startup (to the first hit window), active (or unblockable), recovery, neutral. Windows that reopen
  within a tolerance merge into one hit, so the numbers match at any frame rate. A second row shows the player's own attacks and an
  **I-FR** row shows i-frame cells. Generic: it uses only live probe signals (action id, hit window open, unblockable bit); no per-boss
  table. `[Debug] FrameProbe` writes the same data to the log.
- **Freeze and frame advance** (`practice_freeze.h`; `[Practice] FreezeKey` F9, `StepKey` F6, Practice hub rows): adds an engine stop request that zeroes the
  game time scale while logic and render keep running; a step lets frames through until the meter clock reaches the next 1/60 s cell.
- **Negative Ki meter** (`negki_meter.h`): a thin second bar under a boss's Ki bar whenever either Ki pool is below zero, scaled by the
  effective Ki floor. Read-only.

### 3.9 Return gate, pause and recovery

The "Return" object in an arena is the game's own mission-clear gadget. `gate_zone.h` hides the face buttons from the game inside a zone
around it so the native "This will end the mission" box never opens, and opens the mod's Return page instead (`[Return] ReturnGate*`,
`ReturnGateMaskRadius`, ...). The page adapts to the session mode (`Nioh3Training_SessionMode`): Return to where I was, Fight again, boss
fight options. `[Training] MenuPause = 1` pauses the game while the menu is open during a session. `hazard_guard*.h`,
`player_recovery*.h` intercept native world hazards (for example a void fall) before HP, death or reward side effects, decided by
ownership and native death state, with no map lists; `field_hold.h` holds the player on a long same-world warp target until the
destination cell reports its collision mark.

### 3.10 Recorder and report

`[Record] Enable = 1` starts `Nioh3FightRecorder.ps1` at each Fight now: it captures the primary screen at about 3 fps (half size, JPEG)
into a local folder until the Return completes, the game exits, 90 s after a fight end, or `MaxMinutes`. Only one recorder runs (named
mutex). `fightlog.h` keeps the last 20 fights for the problem report (`[Report]`, which builds a local zip; nothing is uploaded).

## 4. Trip helpers

### 4.1 Keep gear (`src/keepgear.cpp`)

Sandbox missions (tutorial, dojo) call `Item::ReserveAllItem{All,Dojo,Edo}` and `Item::ClearEquipment`, then give the mission's own kit
(`Item::AddEquipment*`, `AddFixItem`, `AddItem*`, `AddMagicItem`, `SetShortCut`, `Player::EquipNinjutsu`, `Player::AddSkill*`,
`Mission::NoDamageMode`, `Player::RequestStyleChange`). While `Nioh3Training_KeepGear()` is non-zero (a mod Fight now trip is running)
those script natives are vetoed (`hooks.cpp` `InstallVeto`). Strip natives are always skipped during a trip and the first one marks the trip as a
sandbox trip; kit natives are skipped only after that, so a normal boss mission's own script rewards are untouched. Decided by what the
script calls, not by a boss or mission list. A safety net runs the game's own restore (what `Item::ResetReserveItem` does) if the reserve flag
went up anyway. The trip state ends on Return or when you leave the trip's world, never by a timer while in the arena. Switch:
`[Rematch] KeepGearInArenas`.

### 4.2 Loot clear (`src/loot_clear.cpp`)

An in-place rematch does not reload the area, so ground pickups from the last round remain.
`Item::CollectAllDropItemInAreaMission` walks one global drop manager and collects type-`0x10` objects; `EraseDropItemInArea` only marks a
box. `Nioh3BossRematch_ClearDroppedLoot` calls the manager's own remove (the function its list uses to free one object) for every
type-`0x10` object, which frees the pickup without granting the item. All four sites are byte patterns; nothing is a fixed address.
Training calls it on retry. A missing export leaves the pickups.

### 4.3 Covers and loading screens

- `transition_cover.h` (BossRematch) is a presentation state machine for the hosted menu: phases Off, AwaitPresent, AwaitNative, Loading,
  Ready, Failed, Cancelled. The Engine overlay draws an opaque quad and acknowledges only a final original `Present` that returned S_OK;
  the game-thread pump posts the Fight request only after that acknowledgment. It owns no native requests, recovery records or saves.
  Cancel, stale or failure clears the presentation only. `transition_native_read.h` holds the passive, bounded readiness reads.
- `[ArenaSwap] EntryLoadScreen = 1` shows the EngineFix loading screen ("Loading boss match", stage = arena name) from the press until the
  player can move; `entry_cover.h` and the `[Fade]` keys (`OutMs`, `InMs`, `MinHoldMs`, `StableMs`, ...) set the black fade.
  `CoverReleaseMs` and `LoadingScreenEndMs` end the native cover or call `UiLoadingScreenEnd` early on a cross-world Fight now.

## 5. Style meter (`[StyleMeter]`, Nioh3Training)

What the player sees: a DMC-style rank (D, C, B, A, S, SS, SSS, with the words Dull, Cunning, Bold, Ardent, Asura, Sword Saint, Heavenly)
and a gauge on the right side of the screen, plus "Bonus +N" pop-ups under it. Hits, clean dodges and Ki pulses raise it; getting hit
drops one rank. It works in any fight, not only Training. Off by default (`StyleMeter = 0`).

How it works (`style_meter.h` pure state machine, `style_meter_game.h` glue, `style_meter_draw.h` drawing, `style_meter_fx.h` pop-ups and
motion; tests `tests/style_meter_test.c`, `style_meter_demo.c`): fed once per frame-probe pump tick from the game clock.
Events: **hit** (the player's hit took HP, from the hit-apply hook), **dodge** (an enemy hit window opened and closed while the player had
i-frames and took no damage), **deflect** (the same, during the universal Samurai deflect: the move's action-row skill word
`[[ctrl+0xE8]+0x20]+0xDC` is in `DeflectSkill`, default `0x67D2`, seen live on all 15 directional deflect actions and never on an attack frame;
`DeflectPts`. The deflect-guard bytes `ctrl+0xEA7` / `+0xEA8` from an outside model never came up live and are only logged), **counter by avoiding** (the same during a skill move: action-row skill word, Spirit Force
or ninjutsu gauge spent; one counter per move together with the hit counter), **Ki pulse** (within `KiHitMs` of a landed hit; a pulse after a whiff scores 0), **startup bonus** (a slower
first hit window earns up to `1 + StartupBonusPct%`), **counter**, **soul core**, **ninjutsu**, **martial art**, **guardian spirit**,
**weapon swap**, **style switch** (only in combat, once per landed hit). Repeating the same action id among the last 8 uses multiplies
points by `RepeatPct` (floor `RepeatFloorPct`); further hits of one swing get `MultiHitPct`. After `DecayDelayMs` the gauge drains
`DecayPerSec` per second, increased by `DecayRankPct` per rank and ramped by `DecayRampPct` per idle second. Rank sizes D..SSS default to
60, 90, 130, 180, 250, 350, 500 (`RankPts` or `RankPtsPct`). Every rule is generic: no per-boss or per-move table. The ini is re-read when its
write time changes (checked every 0.5 s), so edits and menu changes apply without a restart. Drawing is a click-through topmost layered
window; the sprite atlas `style/rank_atlas.png` is embedded with `.incbin` and decoded once with WIC (`style/gen_style_atlas.py` writes
`src/style_atlas_gen.h`).

Layout and look keys (all live):

| `AlwaysOn` | 0/1, 0 | 1: stay on screen all the time (rank D, empty bar) between hits. 0: only while fighting or right after a hit. Menu row "Style meter always on". |
| `StyleMeterX` | -1, 0..1100 (1/1000 of window), -1 = default 880 | Right edge of the meter. Above 1000 pushes the padding off screen. Menu: "left/right". |
| `StyleMeterY` | -1, 0..1000, -1 = default 352 | Vertical centre of the rank letter. Menu: "up/down". |
| `StyleMeterScale` | 25..400, 100 | Overall size in percent. |

Scoring keys: `HitPts` 20, `DodgePts` 45, `KiPts` 30, `KiPerfectPts` 15, `CounterPts` 30, `NinjutsuPts` 20, `SoulCorePts` 40,

`NinjutsuPts`), `RepeatPct` 80, `RepeatFloorPct` 40, `MultiHitPct` 100, `DecayDelayMs` 500, `DecayPerSec` 30, `DecayRankPct` 50,
`DecayRampPct` 150, `DrainPct` 100, `CombatMs` 8000, `DamageGraceMs` 1500, `StartupMinFrames` 15, `StartupMaxFrames` 60, `RankPts`,
`RankPtsPct`, `PopUps`, `Motion`, `PopUpMs` 1200, `ShakePts` 40, `MoveLog` (one "STYLE MOVE" log line per player move). The menu
(Player page, Style rows) exposes the common ones through `Nioh3Training_StyleGet/Set`.

**Boss fight result card** (`style_result.h` pure fight tracker and grade, `style_result_draw.h` card; tests `tests/style_result_test.c`,
`tests/style_result_demo.c`). On with the meter (`ResultCard = 1`). The fight starts at the player's first hit that takes HP off a boss slot
(the hit-apply hook's victim is a `BvActor`) and ends when every boss hit in it is dead (death flag `+0x48`, or gone after HP 0) and no other
boss slot is alive; a boss hit within `ResultEndDelayMs` (3000) of that (a next form, a second boss) continues the same fight. The player
dying, loading, or a hit boss leaving alive drops the fight with no card. Every tick adds `rank + gauge` (D = 0 .. SSS full = 7, idle = 0)
times the game-clock step, so pause, menus and loading do not count and fight length is never part of the score. Grade R needs
`floor(average) >= R` **and** at least `ResultHoldPct` (50) % of the fight at R or higher, so a short SSS burst does not carry a fight. Before grading,
every hit taken subtracts `ResultHitPenalty` (25 = 0.25) from the average, so 4 hits cost a full grade.

the meter's rank-up motion, average, peak, fight time (shown only), time at each rank, and the counts: different moves that landed, martial
arts (and how many different), ninjutsu, soul cores, guardian spirit, weapon swap attacks, style switches, hits, counters, clean dodges, deflects, Ki
pulses (perfect), hits taken. One `STYLE RESULT` log line per card. Menu: Player page "Boss fight result card" (`StyleGet/Set` what 24).

**Recorded drawing** (`[StyleMeter] DrawInGame`, default 1): the meter and the result card hand their finished premultiplied BGRA bitmaps to Nioh3EngineFix (`Nioh3EngineFix_LayerSet/LayerHide/LayerLive`, `osd.cpp`: layer 0 meter, 1 card), which draws each as one textured quad into the game's own frame under the FPS counter and mod menu, so OBS Game Capture records them. Without that API, or while the EngineFix overlay is not drawing, they fall back to their own topmost layered windows (Display / Window Capture only). A layer not refreshed for 1 s is hidden.

## 6. Soul core features (Nioh3BossRematch)

### 6.1 Soul transformations

What the player sees: pressing a soul core d-pad shortcut turns the player into that core's yokai for its attack, instead of throwing the
core and watching a seal-summoned figure. The player model is hidden, the yokai plays its attack under the player's control, then smoke
and the player return. Switch: **Player > Soul core transformations ON/OFF** (`[Spirit] SoulCoreForms`, default 1). OFF means the game's own
soul cores; a form already up ends normally. Compiled only with `BR_SOULCORE=1` (the shipped build).

How it works (`bosslog.cpp`, many `[Spirit]` keys; `src/seal_use_gate.h`, `src/press_queue.h`, `src/spirit_upgrade.h`):

- The Summoning Seal's yokai is a plain `65A8A8` character spawn, not a guardian-spirit script path. A hook on the seal spawn learns the
  core id (`desc[0]`, the character the seal spawns). The chain from inventory item to seal character is read from the game's own
  param tables, with no per-core table: item row (`+0x180` = soul-core param key), soul-core table (`+0x18` = the Yang/seal item), seal
  item row (`+0x54` = spawn character id). `src/form_core_equipment.h` maps equipped item to seal character from copied tables and
  is read-only.
- The transformation reuses the game's own "Living Artifact" form machinery: the form key and model are swapped to the seal yokai
  (`FormKey`, `FormModel`, `FormPart`, `FormAppear`), the player's part slot is replaced with the yokai's body part and rebuilt
  (`FormSlot0`, `FormApply`), the player is hidden with the game's `SetHideModel` (`FormHide`, `FormHidePress`, `FormHideDelayMs`), and the
  form's attack action is requested through the action-state setter. Several `[Spirit]` keys exist only as probes
  (`SlotProbe`, `PartProbe`, `SlotWatch`, `YawWatch`, `Probes`, `FormCommit`, `FormAttach`, `EquipDiff`, `SealIdleLog`, `FormHideActLog`) and
  are 0 in the public ini.
- Exit: the form ends when the yokai's last hit burst starts (`SealExitAtLastHitMs`, observed burst times per core are learned into
  `[SealHits]`, `[SealDur]`, `[SealLastHit]` sections), earlier for a helper actor's burst (`SealExitOnHelperMs`), or on idle
  (`SealEndOnIdle`, `SealIdleEnd`, `SealIdleMinMs`, ...). Smoke effects cover start and end (`SealCoverSmoke`, `SealExitFx*`, `SealExitSmoke*`).
- **Core toss speed**: `FastThrow` (1 to 16) speeds up the throw before you transform, bounded by `RunThrowMaxMs`. `seal_use_gate.h` accepts
  only the player's seal-use animations (`0x28FD`, `0x28B6`, `0x28B2`, `0x28FB`); an ordinary d-pad item must keep native speed, so the
  hook arms a pending check and confirms within `RunThrowConfirmMs` (cap 200 ms), never by a whole `0x28xx` category.
- **Press queue** (`press_queue.h`): a d-pad press made while the previous seal is still in its ghost exit is queued (3 s window) and
  replayed as a 120 ms pulse through the `XInputGetState` hook the first frame the old seal is gone, with up to 4 retries. The old seal is not
  despawned early.
- **Crouch cancel**: L3 within `FormCrouchCancel` ms (default 200, 0..1000, 0 off) of a core press cancels the transformation: the
  player is back at once and the core is not spent; the L3 press is eaten (no real crouch). `FormCrouchCancelKeepCore = 1` puts back a core
  whose count dropped by exactly 1 within 3 s of the press.
- **Camera**: `[SoulCore] CameraFollowVertical = 1` needs the matching `Nioh3CamKiProbe` mod (`mod/shared/soul_camera_vertical.h`).
 
- `spirit_upgrade.h` upgrades an `Nioh3BossRematch.ini` written before the forms existed: only if `SoulCoreForms` is absent, it writes the
  1.8 shipped `[Spirit]` values once; a present `SoulCoreForms` (including 0) is the player's choice and is left alone.

### 6.2 Per-core choice

Rows **Player > Soul core transformation** list the two equipped Yang cores (`Core <hex id> (Yang 1)`, `(Yang 2)`) read from the inventory without
needing a press, plus learned ids and two "not used yet" seal placeholders (LEFT, DOWN). A, Left or Right flips a core between
**transforms** and **game summon**. The choice is keyed by the seal character id in `[Spirit] FormCoresOff` (comma list of hex ids),
never by slot or direction; `FormCoreLeft` / `FormCoreDown` remember the last core seen per direction across sessions. **(source not yet
in the public copy)**

### 6.4 Equip core rows

**Player > Soul cores > Equip core slot / Equip core** swap an owned core into a slot from the mod menu, without visiting a shrine.
Left/Right picks the slot (Yang 1, Yang 2, then Yin) and an owned core; A sends one request. Training runs it on the game thread
(`src/soul_core_swap.h` pure logic with `tests/soul_core_swap_test.c`; `soul_core_swap_game.h` glue, export
`Nioh3Training_SoulCoreEquip`, result codes via `SoulCoreEquipResult`). It replays the shrine handler's valid path in order: the game's "can
this core go in this slot" check; read the d-pad shortcut of the old core; write the slot and rebuild the core list (three calls);
move the shortcut onto the new core (otherwise the old count shows 0); the menu sound and HUD shortcut refresh. Inventory layout used:
equipped slot u32 array at `inv+0x23B6B8` (`0xFFFFFFFF` = empty), item count at `inv+0x927D0`, item record stride `0xF0`; a core is an item
master row with category `900000000` and byte `+0x182 == 9`. Every address goes through `Grva()` (0 = off on another build). Nothing runs
unless the row asks.

## 7. Player log (`[Record]` in `Nioh3Training.ini`)

Records inputs and the player's actions on one timeline, to diagnose "the game felt wrong" reports. Off by default; both keys 0 means
nothing is read or written. Menu: the single **Player log** row in the EngineFix settings (Settings > Game) turns `PlayerLog` and
`PlayerClock` on or off together (`Nioh3Training_PlayerLogGet/Set`; 2 = mixed, one key set by hand).

- `PlayerLog = 1`: `Nioh3PlayerLog.txt` next to the ASI (a new file per game start, the previous kept as `.old`). Line types:
  `SET` (Training version, each mod ASI's size and date, every `[Record]` key, window size, EngineFix fps cap and frame-gen state),
  `PAD` (button edges, held times, left stick in 8 directions with a dead zone of 8000), `ACT` (the player's action id and previous action
  duration, plus animation speed), `WPN` (active weapon slot and Samurai/Ninja byte). PAD and ACT lines end with the fps of the last
  one-second window and the wall time of the newest frame.
- `PlayerClock = 1`: one `CLK` line per second (`player_clock.h`): wall ms versus game ms, ratio, engine clock, fps, worst frame time, stalls,
  the engine's fps-for-dt and counted loading frames. A game frame is counted only when the engine update counter moved. Ratio 1.00 is
  normal; below 0.9 with fps under the cap means the engine is slowing time.
- `player_speed.h` adds `anim 0.61x` to `ACT` lines and an `SPD` line for slow stretches of 300 ms or more: the move's own animation time
  (`[ctrl+0x60]`, 1/60 s units) advanced over wall time, which can show a slow move while fps and the game clock look normal.
- The reader uses its own `XInputGetState` read (nothing masked or injected), the player's action id and step, and the engine update counter,
  on the game thread each pump tick.

## 9. Open problems and known gaps

- **Unverified route classes.** H (hidden duels), D (master duels, hidden-wave stages) and E0 (Picture Scroll waves) rows are gated behind
  `ShowUnverified` or marked "unverified" until `verify_all.ps1` confirms them. 63 of 121 rows carry a `confirmed` date; the rest have no
  recorded live entry evidence on the current fight path.
- **No-route bosses (30 X rows).** 19 are field-only (open-world region missions), at least 5 have no boss record in any shipped mission, 3 have no data,
  and one script leaves its bosses frozen (the remaining rows are of the same kinds). Field-only rows with a picked spawn are summon-only; nothing starts their mission.
- **Staged fights.** The staged-engage chain is generated from script structure; whether every box station fires in a replay with the
  station flags clear is unproven for some missions. One staged mission carries the catalogue warning "Known bug: Death Veil may not
  appear (bar only, wave never starts)".
- **Native actor uniqueness.** Training logs "native actor uniqueness UNPROVEN" when a fallback roster boss is created while the script may
  also place the native one; deletion is exact-placement dedupe and the observer deletes nothing. Fallback roster order is catalogue order,
  and "mission wave ordering unproven".
- **Cross-world speed-ups.** Most `CrossWorld*` keys are off by default because they cause pop-in or are not verified at scale
  (`CrossWorldCellLoads` is marked unverified in the ini comments).
- **Hosted transition cover.** `transition_cover.h` is presentation-only and its test queue (`HostedFightTest`) is opt-in; it is not a general
  loading-screen replacement.
- **Soul transformations.** Several part and appearance mechanisms (`FormAppear`, `FormApply`) are documented as "unproven that the part load
  reads the written field"; the shipped path is the `FormSlot0` capture plus `FormHide`. Forms depend on animation ids and spawn shapes of
  each core's helper actors, so a new core can need learned timings (`[SealHits]` and friends) after one natural use.
- **Frame meter i-frames.** Dodge i-frames are probably hurtbox-based and are not fully covered by the flags the meter reads; the probe code is
  marked unproven in `frame_meter_game.h`. The style meter inherits this for dodge scoring.
- **Not scaled by damage multipliers:** summoned spirits, Ki damage over time and damage-over-time effects.
- **Missing in the public copy:** style meter, Player log, soul-core equip, press queue, crouch cancel, per-core choice, keep gear, loot
  clear, staged start, hazard guard and recovery, entry cover, most generators and generated headers (see the marked sections). The public
  `mod/` is the older add-on 1.5.1 snapshot.
- **No dedicated tech-debt file exists in the source tree.** The list above comes from source comments and the research notes. Per-boss
  special cases are a project anti-goal: when a row misbehaves, fix the generator rule (`pick_fight_start`, `pick_gate`, `pick_arena`, the
  script scan) so every row benefits, and regenerate with `--check`.
