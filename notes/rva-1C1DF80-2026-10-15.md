# RVA 0x1C1DF80 (Nioh3.exe v2.02): character resource release

2026-10-15. Static analysis only. Question from ally, about pc2's bridge file 501. Sources: retained `re/Nioh3.dump.exe` (raw offsets equal RVAs),
`notes/training-boss-spawn-native-contract.md` (follow-up section), `notes/training-yamagata-arena-preload.md` (owner drain),
`notes/boss-swap-re-pc-4963.md` (passive cause), bridge 501, and Training source `captures/pc/b491/x/training.c`. No game launch, no mod changes.

## Bytes (verified in the dump)

```
1C1DF80: 44 8B C2          mov  r8d, edx      ; arg2 -> 3rd arg
1C1DF83: BA 02 00 00 00    mov  edx, 2        ; mode 2
1C1DF88: E9 73 B9 7D FE    jmp  3F9900        ; tail call
```

So `1C1DF80(uint32 chr, uint32 x)` is exactly `3F9900(chr, 2, x)`. It is the inverse of the load request `3F9E58(chr, 2, x)`, which
Training calls directly and `Load::Character` A42A7C calls internally. Size 0xD bytes (functions.tsv: `FUN_7ff75102df80`).

## 1. Arguments

- **chr (ECX) = the character-table scalar**, the same value given to `Load::Character` / `3F9E58` / `CreateDynamic 1C0C5E0` arg0
  (for example 392871 Nuribotoke, 307259 Yamagata). It is **not** a resource key and **not** an actor handle. 3F9900 builds the
  keys itself (`134314`: `0x3_00000000 | id`, with the optional alternate-ID substitution) and walks the same dependency closure
  (`3FB62C`) and type-4 companion list as the load.
- **second argument = 0** at every native caller (`1C217A8` Load::UnloadCharacter, `1C08D1C` owner drain). It goes through as 3F9900's
  third argument, matching the third argument of `3F9E58(chr,2,0)`. Always pass 0.
- No owner/loader argument. It does not touch the script owner's map at owner+3C8. That bookkeeping lives in its callers.

## 2. What it does

It releases **one** reference per call on the character's resource set. 3F9900 calls `3F9A8C` on the ObjectManager (`45B9E60`) for
each key and `3F9A28` on the ActorManager. Inside `3F9A8C` (bytes at 3F9AC4..3F9AE5):
- the resource has not finished loading (`+2C8 == 0`): it increments the pending-release counter `+2C4`. A release before
  readiness is legal and the native code handles it.
- the resource is ready: `3F9A74` decrements the refcount at `+2C0`. When the count reaches zero it destroys the resource and
  removes it from the cache.

Native callers balance it one-for-one with loads:
- `1C217A8(owner, chr)` (Load::UnloadCharacter and UnloadCharacterPlEnemy) calls it once only if owner+3C8 has the key, then
  decrements the count.
- Mission cleanup (`1C10570` -> `1C08D1C`) calls it once for each count still held in owner+3C8.

The mission drain only covers refs taken through the loader (A42A7C). Training's direct `3F9E58` calls (`StartArena` line 569, summon
661, preload 755, `spawn` 917 in b491 training.c) are invisible to it, so they are never released. pc2's file 501 is correct on this.

**Counting rule for a pool.** Training calls 3F9E58 only when `ResEntry(chr)` is missing or not ready. So:
- the ASI holds 0 refs on a boss that was already resident (for example the current mission's own boss);
- the ASI can hold more than 1 ref if a path re-requests while still pending (several spawn/preload calls before +2C8 is set).

Count the ASI's own successful 3F9E58 calls for each chr and call `1C1DF80(chr,0)` exactly that many times. Never release a
character the ASI did not load. That would take the mission loader's ref. The native boss's model could then be freed under it,
and the later owner drain would underflow the count.

## 3. Safe while the boss actor is still alive? No. Despawn first.

The live Character does not visibly hold its own ref on the type-3 character resource. A bounded scan of the factory `2BFA04`/`2BFB88`,
the creation consumer `65A8A8` and `1C0C5E0` found no `3F9C10`/`3F9E58` acquire. The only per-actor resource ref found is a
**type-4** key (`0x4_00000000 | id`): acquired at `2C331E` (stored at live+AB60) and released at teardown `6639B0` -> `663A6C`.
So if the ASI's ref is the last one, releasing it while the actor exists can destroy the model/motion resources under a live actor
(use-after-free). Every native path releases in the order "actor gone, then resource":
- `4BDEB8` cold path: `2BF7E8(live)`, then the resource release;
- mission cleanup runs the owner drain at the end of `1C10570`;
- the spawn contract notes say "Resource release must follow child/request drain".

Safe order:
1. Delete the actor with `2BF7E8` on the game thread. This is synchronous: `2BF818` -> `2BFC90` -> `2BF90C` -> `6639B0` teardown + free.
   It differs from the BD0 deferred path.
2. Make sure no CreateDynamic request for that chr is still queued. A queued request materializes on the next `5BCBAC` drain and
   needs the resource.
3. Then call `1C1DF80(chr,0)` once per held ref, on the game thread. The resource map is locked inside, but the counts are not
   designed for another thread. Doing it a frame later is a cheap safety margin. That a GPU/render consumer could still touch a
   resource in the same frame is not proven either way.

## 4. Relation to the passive boss? None.

1C1DF80 only does resource refcounting. It does not touch AI, side or aggro. The passivity comes from CreateDynamic itself
(`notes/boss-swap-re-pc-4963.md`): `1C0C5E0` copies the **owner's side** `[[owner_live+B0]+10]` into request+60. The consumer
`65A8A8` writes it via `669738`. With owner = player (1) the boss gets side 0 (the player's) and never targets him. With owner = player
there is also no child wrapper (generated ID 0x50000001 has no registry row), so there is no `669A10` attach or `669990` notify.
Every other creation path forces the enemy side (`669510`). The fix is `1C272F0(live,1)` (or `669510(live)`) when the actor appears,
or Training's TeamFix (temporarily setting the player's side to the enemy team during the call).

pc2's 501 probe shows that side alone is not enough: owner = a live enemy (team 1) bosses still did not attack in 60 s at 7 m,
with the player at a shrine. The rest of that gap is BossBattleMode/aware/Algo state and the shrine context, not resources. A
missing or released resource would show up as a missing model or a crash, not as an idle AI.
