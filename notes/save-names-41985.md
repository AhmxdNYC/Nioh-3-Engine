# Named slots and reload study - tasks 41985 / 42000

Implemented on cx-pc/save-names-41985 (code 6f4f22d7): Save files lists up to 64 named slot folders with manifest.json, sorted by name. Picking a name opens Switch after Quit / Switch and relaunch. Existing slot1..slot8 remain compatible; names may contain ASCII spaces (for example Yoritomo Practice). Invalid/reserved/path names and reparse slots are refused. Catalog entries are not claimed checksum-valid until the helper verifies them. More than 64 slots refuses the catalog rather than silently hiding entries. Refresh re-reads the library; Back up current save makes a new timestamped immutable snapshot after exit.

Switch and relaunch is one activation after choosing the slot. It dispatches --quit --relaunch; the helper verifies the originating PID/lifetime, requests WM_CLOSE on its unique visible top-level window, waits for exit0, makes the mandatory backup and commits the switch, then requests steam://rungameid/3681010. It never kills the game. A game Quit confirmation may still need interaction; only pc native acceptance can establish whether it is truly one click on Nioh3/Proton. Launch failure is recorded separately from a completed switch. No live game or installed saves were touched. Defaults Enabled=0 RealRoot=0 remain.

## No-quit reload: feasible native read path found; not implemented or runtime proven

Fresh read-only Ghidra output is in notes/save-names-41985/. RVAs apply to the known v2.02 dump only.

- TitleMenuMode update 1C3413C already submits asynchronous operations through SaveRequest 5B63A8. Its states 0xD/0xF issue op1 then wait; states 0xE/0x10 lead into op5/state0x11. State7 issues op3. This is a state machine with pending/error/UI handling, not a synchronous reload call.
- Startup TitleMode 1C35188 state7 issues op5, state8 waits and issues op3 on success, state9 waits. TitleMode constructor 1C2CB8C initializes sequencer +14=1, and return-to-title path E6B230 constructs this mode and queues replace. The older blanket claim that return-to-title never reloads is therefore unsupported; the path has native reload machinery, although exact branching and profile application still need runtime tracing.
- SaveRequest 5B63A8 -> 5B6CB0 -> 5B6FE0 -> 5B7034 -> 5B7120. Request dispatch selects op0/2 backend RVA470AE10, op1/3 backend4719720, op4 backend4728020, op5 backend4736920. Active backend pointer is RVA45C6EC0. Buffer pointers and the manager request queue persist across calls; 5B6CB0 refuses busy worker +38 and sets manager +10 pending.
- Op1/3 backend vtable3A9AF68 uses UI-side update1FE7014. Its worker1FE6AB4 enumerates metadata, calls 1FE48F8(...,1) for headers, then calls 1FE48F8(...,0) at worker state8 for full data. Op5 has header-only path1FE69E8. An op5-only refresh is not a full profile reload.
- 1FE48F8 -> 1FE497C constructs the save path every call. Header mode reads 0x158 bytes; full mode obtains current file size through1FD9C14 and reads via1FD9C58. **1FD9C58 explicitly calls ReadFile and CloseHandle and requires an exact byte count.** Full mode decrypts with5B85E8/5B88CC and copies plaintext into worker+E0. Thus the full path really re-reads disk; it is not just a cached-header refresh.
- 5B71E0 selects SAVEDATA%02u versus SYSTEMSAVEDATA00 and SAVEDATA.BIN from the request context. Both profile and system contexts need accounting for; not every boot request necessarily refreshes the selected user profile. The final deserialization/application and UI refresh after worker completion remain unmapped.
- **Do not set SaveDisabled then call SaveRequest:** 283950 tests GameMain+3E/+3F and 5B63A8 suppresses dispatch when set. The old phase1 suggestion would block the intended reload. Likewise, my interim bridge note calling op2 a confirmed Load operation was too strong: title new-profile initialization also reaches op2, and it shares the op0 backend; do not use op2 as a reload shortcut.

## Concrete next candidate plan for pc / Opus review

1. Add read-only tracing around native title Load / return-to-title: request opcode/target, backend pointer, ReadFile path and byte count, worker+E0 buffer identity/hash, manager pending->success/error, and profile apply callback. Confirm the same process performs a full selected-profile read, not only0x158 headers. No file writes in this diagnostic stage.
2. Put a transaction coordinator on the game thread at the known title update, after the existing stable main-menu check. Block new menu actions and ordinary save dispatch, drain all existing requests, and require both manager idle and backend pointer null. A scoped permit must let only the transaction's native load request through; global SaveDisabled cannot be used as the load permit.
3. Prepare/verify the selected slot and a full independent backup, then use a new dedicated live transaction adapter with nonce/heartbeat handshake. Do NOT bypass the existing after-exit helper's no-game checks. Abort before mutation on a lost title lease or any fault. Keep original files retained throughout; never allow an old in-memory autosave to race the swap.
4. Re-enter the verified native title/load flow (preferred over calling the low-level reader directly), wait through full ReadFile/decryption/profile-apply completion, then rebuild the title UI and release the transaction guard. Replacing TitleMode is a candidate, not yet a proven sufficient reset. System/profile caches and the selected save index must match the chosen slot.
5. Failure requires verified disk rollback AND reloading the old profile before releasing the guard. If rollback/reload cannot be proven, keep writes blocked and offer clean quit. pc acceptance: disposable copied root first, then authorized real A/B with full backups; assert unchanged PID, expected profile values, returning to title and a subsequent autosave do not restore old-slot bytes.
