# Boss-only loading: Task C static review

2026-10-14, pc2, bridge task 3271. Read-only investigation; no source patch, build, game launch, native call, installed-file change, or save access.

**Verdict:** use an existing native duel mission where one exists. The data contains **19 mission records with exactly one enemy record and one boss candidate**; this is the least-risky boss-only *content* route, not proof of a smaller world footprint or faster loading. For repeated fights in the same arena, preserving the scene and re-entering the full native encounter is the most relevant research direction, but no complete reset is established. There is no defensible generic loader-bypass patch yet. The reported **16.297 / 19.612 s** include intro and readiness, not just resource loading (`notes/rematch-fast-restart-2026-10-13.md:9`).

## What the decompiles actually establish

1. `MissionRequestById`, RVA **0x2239600**, selects a default start only when arg3 is zero, finds the mission record, packages mode 2, mission and start, and calls `MissionRequestEnqueue`. There is no same-ID resident-scene branch in this wrapper (`decomp/0x2239600.c:34`, `:49`, `:56`). The third argument is a start point, not an enemy filter or smaller-load selector.
2. `MissionLoadStep`, **0x223AF50**, first checks **0x1FC6674(stage+0x500)** and **LoadIsLoadEnd 0x3B3424**, then runs substantial character/mission setup including `MissionSetupEmaki`, and only at the end writes sequencer mode 6 (`decomp/0x223af50.c:35`, `:87`, `:174`). It is a gated setup/completion phase in the wider load sequencer. Timing only this function cannot attribute the whole loading interval. Returning early, jumping to mode 6, or forcing readiness would omit required work; none is supported by the evidence.
3. `EmakiMissionRequest`, **0x10DBED0**, resolves the record; its `+0x0C` feeds the start-point argument. It writes **mission 0xCC96** and mode 2 into the same three-slot, 0x58-byte queue, regardless of the record's start point (`decomp/0x10dbed0.c:100`, `:124`, `:139`). It supplies no alternate cheap mission loader.
4. Full *mission initialization* does not establish full *world-cell loading*. The newer installed spawn override already chooses the arena streaming center through **0x223B8F0 -> WorldGridFindCellContainingPoint 0x3A1700** (`notes/rematch-fast-restart-2026-10-13.md:67`; `re/symbols/symbols.tsv:1612`). The exact currently selected cell set needs observation before proposing to remove any.

## One concrete experiment: trace a native same-arena retry, with no behavior changes

**Proposed only; not executed or implemented by this task.** At the next separately authorized game turn, use one solo/offline Yoritomo replay, **R7B35, mission 0x7B35, boss 375545, start 374664, box 371660, door 62177372** (`notes/rematch-fast-restart-2026-10-13.md:29`). Sequence: first entry -> native loss/retry -> second native loss/retry -> win/leave. If the known retry defect prevents a second fight, end with that observed failure; do not manually start scripts or manufacture a boss to complete the trace.

Use the existing BossLog/LoadStats/LoadGates observers plus the smallest new pass-through set needed for owner correlation: **2239600**, **223AF50**, **223B8F0/3A1700**, **94B04**, **95244**, **E22D10**, **1C10570/1C08D1C**, and **1180740/669110/669388**. Reuse already instrumented sites rather than installing duplicate detours. Filter script/placement events to the target owner's generation and relevant start/clear/mission_end tasks; accumulate frequent readiness/cell calls in memory and emit only changes/interval summaries. No game-memory restoration, forced readiness, queue rewrite, callback suppression, HP write or artificial re-entry.

Record, per first-entry and retry generation:

- QPC at request, load start/end, first stage/object readiness, boss-mode start and independently observed player control. Report request-to-control separately from the 58A cover interval and intro duration.
- Start record/stream center and selected cell IDs; active scene/mission owner and resource handles with release/create events. An unchanged address alone is not proof of surviving residency because allocators reuse addresses.
- Named start/clear/mission_end context creation/completion/release, boss wrapper/object creation/disposal, native gate poll/right events from the existing rematch logger, and player recovery state. `mission_end` must not be confused with deleting a single coroutine.
- Loader queue/character/object readiness after resource managers drain. Older Continue-load measurements show 14.6-16.3 s after manager drain, but those are **different loads** and cannot explain the rematch's 16-20 s without this trace (`notes/loading-bottleneck.md:27`).

**Decision from this experiment:**

1. If the streaming center is already the arena and no broad cell workload is observed, reject "load the boss cell instead of the world" as an unsubstantiated optimization.
2. If owner/resource release occurs on retry, ordinary retry does not establish a reusable resident encounter. Do not keep stale pointers or skip teardown. Separate native retry correctness work from the no-load project.
3. If scene/resource generations demonstrably survive, and native cleanup/player recovery complete, map the remaining start/clear/gate reset obligations. Only after all are established propose a separate owner-bound native-script re-entry experiment; this trace alone does not authorize or prove one.
4. If most time is intro/cover/script sequencing with loaders already ready, selective world loading is the wrong target. Preserve player protection and investigate only the measured interval.

Acceptance for this **logging** experiment is an attributable timeline (including failure), unchanged native results, and no dropped probe events; there is no invented speedup target. A later gameplay optimization must show the correct boss, two working retries, phase transitions, playable control, one legitimate clear/reward sequence and clean exit.
