# amrita.tools: Nioh 3 save editors and game-data reference sites

Status: investigated 2026-10-06. The page HTML, JS bundles, WASM modules, JSON and the public read-only `GET` API catalogs were
downloaded as text into the session scratchpad and parsed statically (custom WASM disassembler, JS-literal parser).
**No downloaded code was run.** Nothing in the game folder or the running game was touched. Name lists are in
`re\symbols\amrita\` (README there). Exe functions found from their constants are in `re\symbols\incoming\amrita.tsv`.

**Bottom line for the performance project:** nothing here is a performance lever. The value is (a) a full description of the
**user-save format** (encryption, checksum, tagged-record layout) and the exe functions that read and write it,
(b) **~9,000 gameplay-id → name rows** (items, gear effects, skills, soul cores, sets, enemies) keyed by 16-bit param ids, and
(c) one timing fact that supports our frame-timing work: **buff timers count down by the frame delta, kept in 1/60 s units** (§4).

## 2. Save format (SAVEDATA.BIN, PC user save)

Path: `%LOCALAPPDATA%\KoeiTecmo\NIOH3\Savedata\<steamid>\SAVEDATA00\SAVEDATA.BIN`. This matches our `BuildSavedataUserDir` (0xfb95c0).
Recovered from `nioh3_savecore.wasm` (32,587 B, exports `wt_open/read/read_stride/find/write/finalize/checksum/equip_span/equip_index_bitmap`).

| Item | Detail |
|---|---|
| Minimum size | `0x900198` (9,437,592 B). The file is a fixed size: header + 9 MiB body + 8-byte trailer. |
| Header | Bytes 0..0x157 (344 B) are XORed with a 344-byte key. After decoding, bytes 0..5 = **`RNNUSR`** (user save) or **`RNNSYS`** (system save). "RNN" is the Rise of the Ronin lineage. +32 u32 savedAt (unix time), +40 u32 saveCount. |
| Body cipher | A block cipher over the rest: the WASM carries the AES Rcon table (01 02 04 … 1B 36) and no S-box (fixsliced Rust `aes` crate style). Key material is a 632-byte blob deobfuscated at start-up by an LCG (1664525, 1013904223 = Numerical Recipes). We did not extract the key; it is not needed for perf work. |
| Checksum | u32 at `0x900194`, over the **decrypted** buffer. `seed = u32@0x900190`. `acc = 0`. For each of 9216 blocks of 1024 B starting at 0x190 (block base B): `a = Σ_k u64@(B+32k+0x08) + u64@(B+32k+0x18)`, `b = Σ_k u64@(B+32k+0x00) + u64@(B+32k+0x10)` (k=0..31, wrapping u64), `acc = (b + acc + a) ^ seed`. Result: `u32((acc / 0xFFFFFFFF) + acc)`. (Algorithm from `wt_checksum`/`wt_finalize`, func 14/18.) |
| Body | From offset **400** (344 + 56): a flat stream of tagged records `{u32 fieldHash, u32 size, u8 data[size]}`. Records nest (learned skills, shortcuts, soul-core history use the same tagging inside). |

Field hashes, layouts and the exe sites: `re\symbols\amrita\save_field_hashes.tsv` (22 fields: inventory 2500×240 B, stats,
baseStats, guardians, learned skills, presets 19×32976 B, shortcuts, equipped gear 2×17 slots, Picture Scroll array,
soul cores, soul-core Transformation history 2000×28 B). Gear item records: `u16 id`, qty, level, plus, flags, rarity (+48), and **7
effect slots** of 24 B at +56 (`u16 effectId, u32 value, u8 q, u8 cls`, cls bit 2 = star grade).

## 3. Save format in the exe (new symbols)

Every save field hash is an immediate in `Nioh3.exe` (dump at `re\Nioh3.dump.exe`, scanned as bytes). The hits cluster in a few functions.
These rows are now in `re\symbols\incoming\amrita.tsv`:

| RVA | Name | Evidence |
|---|---|---|
| 0x1044680 | SaveUserReadPlayerSection | 14.5 KB; `mov edx,<hash>; r8=[r14]+off; call reader`, e.g. stats → +0x94, baseStats → +0xB0 |
| 0x105ae20 | SaveUserWritePlayerSection | Mirror with the same hashes; calls SaveWriteSoulCoreHistory. Both share 4 callers (0x106d7a0, 0x106e9d0, 0x106dd30, 0x1072340) |
| 0x1047f30 / 0x105ec60 | SaveUser{Read,Write}EquipSection | equippedGear, soul cores, shortcuts |
| 0x103e660 / 0x1055780 | SaveUser{Read,Write}InventorySection | inventory |
| 0x104d470 / 0x1064eb0 | SaveUser{Read,Write}ScrollSection | scroll array |
| 0x104dfa0 / 0x10651a0 | SaveUser{Read,Write}PresetSection | presets |
| 0x6bbccc / 0x20ee380 | SaveWriteInventoryArray / SaveReadInventoryArray | hash 0x938A61DD, 600000 bytes |
| 0xa58a34, 0xa55b94 | SaveWriteEquippedGearBlock, SaveWriteSoulCoreHistory | hash, count, array |
| 0x6bc190 | SaveStreamWriteU32 | 297 callers; writes each record's hash/size |

The direction (read vs write) is inferred from the helpers each function calls: medium/low confidence. Merge with `py re\symbols\merge_incoming.py`.
The hashes are **not** in our property/type DBs. Our property hash is `h = Σ c_i·31^(i+1)` (verified: G→0x899, EV→0x14B31,
FramePerSecond→0xBA590864, 5,977 DB names match). A meet-in-the-middle dictionary attack (26k words, 1–3 tokens) found only chance
collisions, so these field names use another vocabulary or another hash.

Perf relevance: the save system is the `SaveLoadThreadMain` worker (0x5b7390), and it writes a fixed 9 MiB buffer.
Autosave costs one 9 MiB serialize + encrypt + write on that thread. That cost was not measured, and the work is off the main thread.

## 4. Gameplay "effects" and buffs: is this a CPU cost? No.

- The "effects" on these sites are **gear stat modifiers** (319 effect kinds, 1,374 roll rows, a 501-level value curve), not particle
  effects. Per character they are bounded: ≤7 slots × 17 equipped slots × 2 styles, plus set/grace bonuses. They are numbers
  aggregated into stats, not per-frame simulations.
- **Buffs** (scratchpad "Buff conflict groups", from table `entry_0080` joined to category table `entry_1072`, names from `lang_0165`):
  406 buff records in **194 categories**. **The game keeps one instance per category**, so a character never holds more than
  194 active buffs, and in practice holds a handful. There is no unbounded effect list to iterate. Not a hotspot candidate. (We have not checked
  `notes/cpu-profile.md` for the buff update function by name.)
- **Timing fact (frame-timing relevant):** "Duration is the record value divided by 60: the buff timer counts down by the frame delta,
  which the engine keeps in sixtieths of a second." This matches our finding that the game advances a fixed 1/30, 1/60 or 1/120 step per
  frame (`notes/frame-timing.md`). Below the fps target, buff, ailment and other gameplay timers run slow in real time too, not only
  movement and camera. A correct variable-delta fix therefore also fixes buff durations. A partial fix (camera only) would leave the timers
  desynced.
- Other engine facts on the scratchpad: Ultimate Constitution's current-HP regen path "is disabled by a parameter"; rank letters are
  `lang_0003.bin` indices 1472–1495 (`rank = LADDER[value+6]`).
- The tools expose **no** AI update rates, spawn counts or VFX budgets. `enemies.tsv` (142 names/ids) exists only so the scroll tool can
  reproduce Crucible wave and reward RNG (`nioh3_seedcore.wasm`: `init/search/feasible/set_enemies/region_of`).

## 5. Can these tools hurt a player's performance? Practically no.

- Every save array is **fixed-size** (inventory 2500 slots, history 2000 entries, 7 effect slots per item, 19 presets). The file
  size is fixed (9 MiB) and the tools only overwrite bytes in place, so an edited save cannot carry a "huge effect list".
- The scrolls/weapons tools restrict output to rolls the game can generate. The soul-core "repair" flips one u8 per history entry.
  None of these add objects or per-frame work.
- The real risks are gameplay/online-integrity risks (illegal or edited gear in co-op) and save corruption. All tools verify the checksum
  round-trip, and the site tells users to back up first. Not a perf concern.

## 6. How this helps our tooling

- **Symbol DB:** 15 new exe functions (save serializer) in `incoming\amrita.tsv`, and 22 save field hashes with layouts. No new KTID,
  type or property names: the gameplay ids are a separate 16-bit param-id space, not KTIDs.
- **Data editing tools:** if we ever decode the LFM-layer param tables (`archive\…`; game-data.md says "game tables" live there),
  `items.tsv`, `gear_effects.tsv`, `skills.tsv` etc. give names for their 16-bit row ids, and amrita's names `entry_0080` (buffs)
  and `entry_1072` (buff categories) tell us those tables exist. Their entry numbering is their own and was not mapped to our `lfm_list.tsv`.
- **Save-based testing:** with the checksum and layout above, a perf test could patch a save (e.g. a fixed loadout, or the same spawn point)
  for reproducible benchmark runs without touching game files. Decryption would need the AES key from the exe or the WASM. Not done.
