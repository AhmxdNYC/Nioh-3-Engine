# Crash 2026-10-18 01:56: summoned boss killed -> shrine rest -> "Fatal error" (Nioh3Training bug)

Analysis only. I did not launch or modify anything. Evidence is in `captures/crash-20261018/`.

## What it really is

- The game did not exit. PID 8424 (started 01:45:57) was still alive at 02:05. Its game thread was stuck inside
  the game's own **"Fatal error!" message box** (`#32770`, title "Nioh 3 v.2.02"), which sits behind the
  fullscreen window, so the game looks frozen:
  `[Code] 0xC0000005  [Address] 00007FF9F0E1E15E`.
- `Nioh3.exe.16804.dmp` is **not** this crash. It is from 2026-10-17 11:10 (a different session). That one was a
  `__purecall` -> `abort` (C0000409 / fast-fail 7) in the renderer retirement worker 1A757B8 -> 532C64 ->
  4C7548/4C858C. It is engine-side and unrelated.
- For this crash I wrote two small thread dumps with MiniDumpWriteDump (read-only), `hang-8424-a.dmp` and
  `hang-8424-b.dmp`, and read a few values with ReadProcessMemory.

## Fault

- 7FF9F0E1E15E = **Nioh3Training.asi+E15E** (the deployed build from 01:45:46, ts C7E276A5).
- It ran on game thread 13676, the Training pump thread, called from the AI path (ConditionCheckById F68D8 ...).
- The exception record recovered from the stack is a read access violation at FFFFFFFFFFFFFFFF, meaning the
  pointer was non-canonical.
- Context at the fault: r11 = FB86000000000000, r10 = Training+68530 (`g_sp_actor`), r9 = 0x10 (index 2),
  rsi = player.
- The faulting function is E0D0..E1D0 = **`MvBossChr()`** in `src/move_toggle.h`, called from the move-select
  hook `h_mvsel` -> `MvRepeatPick`:
  ```
  E152 mov r11,[r11+3B0h]   ; actor->ai
  E15E mov r11,[r11+8]      ; ai->ctrl   <- AV (ai = FB86000000000000)
  ```
- Live process memory confirms it: `g_nsp` = 3, `g_sp_actor` = {0, 0, **1F9C1B450F0**}. That is the REA75 boss
  (spawn #2). Its object is freed: vtable 0, +3B0 = FB86000000000000.

## Two mod bugs (both in Nioh3Training)

1. **Stale `g_sp_actor` entry.** The REA75 summon died at 01:56:07-11 (BBM END) and was never despawned. The
   shrine rest at 01:56:40.9 reloads the area, which frees the dead dynamic actor. The game thread froze at
   ~01:56:41, shortly after the respawn `Load::Character` calls. Nothing in Training removes freed actors from
   `g_sp_actor`/`g_slot_act`. Only `Despawn()` nulls them, and it already has the right "still in the actor
   table?" check (training.c ~301). When the respawned enemies picked moves, `MvBossChr` walked the stale
   pointer.
2. **The `Rd64()` guard did not work here.** `Rd64` (training.c:78) uses `__try/__except`. zig clang -O2
   inlined it into `MvBossChr`, and the inlined copy has **no SEH handler** (the .pdata unwind for E0D0 has
   flags 0). The "safe read" became a plain `mov`. Only 59 of the 716 functions in the binary have a handler, so
   other inlined `Rd64` calls are probably unprotected as well.

SummonNoDeath and the boss record are not involved. NoDeath only kept the player at 1 HP. BossRematch and
EngineFix threads were idle.

## Smallest fix (`nioh3-combined/mod/Nioh3Training`)

- training.c:78: `static __attribute__((noinline)) int Rd64(...)`. Do the same for every helper that relies on
  `__try` (Rd32, RdF, and so on). This restores the guard at every call site. To check: rebuild, then confirm
  that E0D0-equivalent code calls Rd64 and that Rd64's .pdata has EHANDLER.
- Prune stale summons on the game thread. Add a tick next to `SumNoDeathTick` (pump, line ~4245): whenever
  GAMESTATE[2] goes 0->1 (a load or shrine rest), and also every ~500 ms, drop every `g_sp_actor[i]` that is not
  in `Actors()`. Use `SlotForget(a); g_sp_actor[i] = 0;`, the same as Despawn's "already gone" branch, and log
  it. Optionally, `MvBossChr` can also skip actors whose `+0xAB84`/HP check fails.
- Both are mod bugs. The engine's own top-level handler only reported the AV.
