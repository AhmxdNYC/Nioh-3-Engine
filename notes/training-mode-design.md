# Training integration: observer first, one native-arena practice route

2026-10-11, Codex. Design only at `1641d3f`, branch `codex-training-core`; no source edits, build, game run or new native ABI. Root owns integration. Read with [inventory](training-mode-inventory.md), [spawn contract](training-spawn-contract.md) and [stage contract](training-stage-contract.md). Companion notes are separate deliverables.

## Evidence boundary

The base add-on is `Nioh3BossRematch` 1.3.3, not EngineFix. The implementation target is current `rematch-instant` 1.4.0, inspected without changing this worktree. Source references below are relative to `mod/Nioh3BossRematch/` at that branch unless explicitly marked base. `src/main.cpp:101` resolves sites, registers BossLog, starts rematch and conditionally starts the overlay; `src/rematch.cpp::Start:1537` returns immediately when `[Rematch] Enable=0`. Therefore merely adding observer code to the current rematch tick does not support an independent observer.

E1 v4 was inspected with `git show rematch-instant:<path>` at `b2cfe097ad93dd89b4753e49f43a2cfa93c8ea75`; it is absent from this base. Its build note documents the 2026-10-10 R1CBC one-boss PASS: arena spawn, zero warps, 24.5 s request-to-fight, retry ID 67064 preserved, record restored on leave. This is evidence for that run. The same note explicitly queues full death/retry, camera, save-diff, all-row and Proton checks. `spawn=arena` only means more than five horizontal metres from the original start; `FnVerify` PASS only means the global BossBattleMode counter increased. Neither validates the arena, target placement or actor lifetime. Do not describe v4 as generally validated or assume its code is integrated here.

Two distinct modes are needed:

- **Observer:** no game-state writes or native game calls; hook installation and local diagnostics only.
- **Native mission practice:** experimental replay/restart convenience with ordinary mission persistence. A reward-free sandbox requires separate prevention and save/script proofs and remains unavailable.

## First implementation unit: independent read-only observer

Startup settings are proposed as `[Training] Observe=0` and `Enable=0`. `Observe=1, Enable=0` permits only the observer. `Enable=1` does not enable unavailable mutation capabilities. General module enable remains required. The unit must work with `[Rematch] Enable=0`, all Debug logs off, Remote Pipe off and no overlay/controller changes. It must not read or execute stale Rematch SelfTest settings. Existing independently enabled rematch features may still mutate; observer telemetry must identify that source and claim only that the observer itself writes no game state.

Exact integration seams for the source owner:

1. In `src/main.cpp::Init`, after `ResolveAll` and `bosslog::Register`, resolve observer CORE/FIGHT/PUMP prerequisites and register its handlers **before** installing FIGHT. Require `g_img.knownBuild` for this experimental unit plus all required resolved groups; report feature off with the first reason. Unknown-build pattern resolution alone is not runtime training approval.
2. Share v4 `ReadSnap:159`/`PlayerPos` read layout, augmented with validity bits for GameMain bytes, mission, all three queue slots, player, PlayMode, NetMgr and scroll state. Read them only on the pump for training; publish copied POD snapshots for UI/pipe. Missing reads are `unknown`, never offline/zero/no actor. No `CallCleared`, `CallWpFind`, replay menu virtual call, warp, rights request, mission request or return is executed by the observer. Load the TSV with the pure parser for metadata; label clear eligibility unknown unless valid cached evidence already exists.
3. `src/hooks.cpp::InstallPump` stores a single `g_tick` and is not a multi-subscriber registry. Install it **once** with a dispatcher owned by `Init`. Move v4 rematch pump installation out of `rematch::Start:1537`; expose current `Tick:1304` as a module callback and distinguish prepared versus pump-live state. Dispatcher samples the observer, invokes rematch's current tick only when rematch successfully prepared and enabled, then publishes observer events/snapshot. Preserve the existing thunk's original callee/chaining and its reentry guard. Observer-only startup must not invoke rematch `Tick`, `ToIdle`, scanning, `TrackReplay`, `SelfTestTick`, `SpawnTick:1267`, `SpawnApply:376`, unhide or map writes. In particular v4 calls `SpawnTick` before legacy request consumption: keep it entirely inside the enabled-rematch callback, never in shared observer sampling. On pump failure neither feature is live; installed entry hooks remain passive.
4. Append scalar-only observer handlers with `OnEntry("Character::Create", ...)`, `OnEntry("BossBattleMode", ...)` and `OnEntry("BossBattleModeEnd", ...)`. Existing `bosslog::Register` always registers FIGHT bookkeeping; install FIGHT once when either feature needs it. Entry callbacks copy placement ID, integer argument values, event sequence/time and observed epoch into a bounded local event ring; they perform no game calls, pointer traversal or synchronous file logging. Caller-thread identity is diagnostic: do not assume all entry callbacks share the pump thread. Publish through a short lock or another proved multi-producer mechanism; a contended/full ring drops an event and increments a loss counter.
5. Add training query dispatch in v4 `src/rematch.cpp::Command:1837` **before** its `!g_live` return; `src/remote.cpp::Client` can remain a line/reply transport. `training status` reads the cached snapshot/receipts only. `training submit <boot> <sequence> snapshot` posts an observation request to the pump and returns its admission ACK, not completed telemetry; `training result <boot> <sequence>` reads its receipt. This first unit refuses every mutation kind as `unsupported_read_only`. Existing `[Remote] Pipe=0` remains unchanged. Persist compact diagnostics through existing `Log` from a non-game diagnostic consumer of copied events; use bounded buffering and expose losses. No captured arena/verified file writes occur in this unit.

This is a small integration refactor of existing initialization/pump boundaries plus observer state, not an external C ABI or an arbitrary spawn scaffold. Its first delivery need not expose a new menu. A later picker may reuse `UiFill` and its selection model; the overlay's input/IAT code is outside this unit.

Epochs are observer-owned counters, not game identifiers: increment mission epoch when a valid mission identity changes; load generation on every load rising edge; session generation on any valid session change or loss/recovery of session validity. Clear the current-attempt placement set at each boundary. Entries outside a readable stable mission are tagged transitional. Any sampled table/wrapper/Character address is a diagnostic identity valid only for its sample; never cache it for later dereference or ownership. A same-mission retry still changes load generation. Begin/end imbalance is reported; the observer does not repair game state.

## Deterministic command and acknowledgement contract

Training ingress uses one bounded FIFO of eight copied commands guarded by a short SRW lock; UI and pipe use the same admission routine. Copy kind, row ID, descriptor digest and admission epoch/expected mission into each request; revalidate them on consumption, never retain a UI row pointer. Mutation capacity is one active transaction; snapshots may queue beside it. A completed start keeps a practice-session lease identified by its start request ID; restart/exit must name that session and become its next transaction. Unrelated starts/legacy mutations remain refused until departure and cleanup release the session. The pump consumes at most one new command per tick and advances the active transaction, so it never invokes two competing mission calls in one tick. Reject queue full, invalid arguments or busy mutation explicitly. Do not adapt training to the legacy overwriteable request word.

Use `(boot_id, sequence)` as the request identity. The status reply includes `next_sequence`. Under the admission lock, a submitted new ID must equal that value; allocate/advance it only on successful admission. UI obtains its ID through the same locked routine. Same retained ID and identical payload returns the existing receipt without enqueueing; changed payload is `id_conflict`. An older evicted ID is `receipt_expired`, never re-executed; a future ID is `sequence_gap`. A different boot ID is `stale_boot`. Retain the latest 128 terminal receipts plus every nonterminal receipt; also pin any receipt associated with an unresolved lease/cleanup, even when its operation outcome is terminal indeterminate. These rules make competing pipe clients, retries and double-clicks reviewable. A transport disconnect does not cancel or resubmit work.

Lifecycle is `submitted -> consumed -> validated -> issued -> native_accepted -> loading -> landed -> ready`, with terminal `completed`, `refused`, `cancelled_before_issue`, `failed` or `indeterminate`. The immediate transport response is `ACK accepted id=<boot>-<sequence> stage=submitted`: accepted means admission to the add-on queue only. Observer snapshot skips native stages and completes when the pump publishes a fresh valid-or-explicitly-unknown snapshot. `issued` means the native call was invoked; `native_accepted` requires its queue postcondition. `completed` means the operation-specific observable predicate passed. Later status/receipt queries expose these stages; never use a toast or a returning void function as completion evidence.

Refuse permanent conditions immediately on consumption. For an otherwise eligible request, defer a transient busy/loading/paused gate for at most five seconds, then refuse with the last gate; do not wait online/unknown-session commands until the player later becomes offline. Validate again immediately before **each** native call/write. Before issue, cancel simply removes the owned request. After a mission request is accepted, cancel cannot retract it: acknowledge `too_late`; a separate tracked exit can run only under its own safe gates. A call exception or lost post-call queue read can mean side effects occurred: report `indeterminate`, retain the mutation lease, observe transition/cleanup and never automatically repeat the native call.

For a mission start, require the expected free 0x58 queue slot to contain mission, nonzero requested start and mode 2 (`FightSlotOk`). Current `ExecDirect` only warns on a start mismatch; training must reject readiness and report `accepted_wrong_start`, because the game may already be loading an ordinary replay. Preserve transition ownership and allow tracked exit rather than falsely claiming refusal had no effects. No load within 120 s, or no stable landing within 20 min of issue, ends the start receipt with timeout/indeterminate evidence; it does not authorize rewriting actor flags. Fight verification uses play time excluding loading/pause: 60 s after arena entry, or 180 s after a real door-right request. Missing required placement events or ring losses invalidate strict ready evidence.

All mutation producers need one shared lease: training, rematch menu/pipe and self-test must reject competing new starts/exits while another owns transition/restore. Check legacy `g_req`, `g_pend` and `g_state` at admission and consumption; block legacy `Post` while training owns the lease. Observer queries require no mutation lease. This arbitration is a prerequisite for later practice, not necessary to enable read-only observation alone.

## One native-arena boss practice workflow

The only initial allowlist entry is `R1CBC`: Yamagata Masakage, mission `0x1CBC`, placement **65092**, retry/start **67064**, arena gate **66599**, kind **box**. Placement 65092 is data, not an executable RVA. Use the effective parsed row plus a pinned provenance/digest; the base shipped arena point and the v4 test's captured point differ, so do not hard-code the test log's coordinates as a newly validated descriptor. Require the selected mission cleared on the current journey using the existing game-thread getter immediately before request.

1. Observer collects a baseline in an offline eligible save. Picker exposes the single native arena and its single native boss. Start remains unavailable unless the native-practice capability, current row descriptor, required sites, full actor/stage observations and acknowledged ordinary replay persistence policy are enabled. The label is **Native mission practice (experimental)**; it does not promise reward suppression.
2. Acquire the mutation lease and submit one start. Target current v4 `ExecDirect:677`/`CallRequestById` with the existing current journey byte, start 67064 and aligned parameters. Require exact queue acceptance, observed load and readable stable landing in mission 0x1CBC. Arena-first practice additionally requires enabled FightNow/Warp/Spawn and resolved CORE/FIGHT/PUMP/FNOW/WARP/SPAWN/EXIT; GATE is not required to force this native box trigger. Validate v4 `ResolveSpawn:336` and record ownership before enabling this capability. SPAWN failure/fallback preserves ordinary rematch behavior but refuses the arena-first practice claim. Base 1.3.3 can supply observation evidence; it is not the implementation target for this workflow.
3. For v4, temporarily own only the verified start record's +40..4F position/yaw and +8 camera flag; preserve retry ID 67064. Keep the override's lookup/identity/byte checks, record provenance and restore telemetry. The native arena box should initiate the game's intro and boss flow. No forced rights key, activation/reset call or new actor construction is needed for R1CBC. An unexpected fallback is reported as degraded arrival, not arena-first success.
4. Declare attempt ready only after expected mission/landing, a new BossBattleMode begin and expected placement create-entry in this generation, with no loss/duplicate ambiguity. This proves observed native fight start, not exactly one live actor. An authorized later runtime check must also inspect gate behavior, AI, animation, navigation, player visibility and camera. Unexpected duplicate activation entries fail the candidate gate pending explanation; absence of duplicates is not ownership proof.
5. Native player death/retry is observed as a new load generation, never implemented by clearing ReceivedDead or restoring HP. Rearm readiness only after the same mission, a fresh landing and fresh native fight evidence. Scripts may legitimately choose a different retry point; report it and suspend the validated arena-first claim until the descriptor supports it. Repeated death/retry remains an explicit runtime gate, presently unproven by the v4 one-boss run.
6. A requested restart uses a two-part transaction: call existing native Return once under EXIT/offline/loading gates, require a valid changed +28 mission ID for five continuous nonloading seconds, readable player, rematch idle and restore completion, then recheck clear/session/queue and submit the same mission once. A free queue slot means +4 mission=0 and +8 byte=0; consumed slots can remain occupied, so do not require all three slots empty. Never send another MissionRequestById into an ongoing fight or treat same mission ID as restart completion. If Return does not reach a supported nonzero eligible mission, stop as `restart_needs_manual_resume`; do not invoke Continue or invent a return destination.
7. Exit uses Return and the same departure/restoration predicate, then releases the lease. It does not prove a particular hub destination. Title/save changes, missing actor-end events, reload and failure clear only observer/session state; native actors remain owned by the game. Online/unknown-session transition stops further game calls, cancels unissued work and suspends readiness. Already owned local record restoration is the sole cleanup exception and must satisfy the fresh identity/byte check; no native return, warp, rights or spawn call is allowed while unsafe. If restoration cannot be proved, report `cleanup_indeterminate` and block another mutation lease.

Restore ownership must be stricter than v4 `ToIdle:620` and `SpawnRestore:417` silently forgetting failure: record replacement or current-byte mismatch means relinquish without overwriting someone else's state; a failed write leaves cleanup unresolved. Reapplication must distinguish original baseline from the add-on's own bytes and a newly loaded record; never snapshot owned bytes as the original. Root must audit v4's `SpawnApply/SpawnRestore` for that case before incorporating it into practice. No actors or stale record pointers survive a transition in mod ownership. Hot unload/reinstall is unsupported; module/config changes happen while the game is closed.

## Persistence and release gates

Observer writes only local diagnostic state/logs and installs pass-through observation hooks. It never changes the catalogue, captures, verified TSV, game configuration, save or cloud data. Recording normal game save events does not prevent them.

Native practice permits normal replay effects only after the user/runtime protocol accepts that policy: playtime, retry point, inventory, currency, drops, clear/reward/script events and autosaves may change. Do not suppress selected reward calls and assume completion/achievements are isolated. A future sandbox needs an exhaustive write/effect inventory, verified prevention or isolated supported save context, native actor cleanup and compatible boss-script completion; none is currently proved. Backups and test restoration are managed by the authorized runtime lead, outside this implementation unit.

Concrete acceptance tests for the implementation owner (not run by this design task):

- **O1 defaults:** Observe/Enable both omitted or zero installs no training hooks/pump subscriber, starts no UI/pipe and issues no training native calls. Existing rematch opt-in behavior is preserved.
- **O2 independent observer:** Observe=1, Rematch Enable=0, Debug logs off, Remote Pipe=0, stale Rematch SelfTest present: observer boots, FIGHT/PUMP installs once, no SelfTest/scan/game calls, no controller hook, captures/verified files unchanged.
- **O3 pass-through/failure:** missing CORE/FIGHT/PUMP, unknown build and simulated hook failure produce an exact disabled reason and no live observer; original pump callee executes once. Observer/rematch together still use one dispatcher. Reentry/handler exception does not produce a second game call.
- **O4 validity/epochs:** unreadable PlayMode/NetMgr/queue/mission and stale pump remain unknown; online transitions refuse mutations. Same-mission retry increments load generation; mission/title/save/session changes invalidate observations. Old placement IDs cannot satisfy new-attempt readiness.
- **O5 bounded observation:** synthetic >capacity events and concurrent entry writers yield explicit loss counts without blocking the game thread or malformed records. Entry observations never imply live count, allocation success, death, actor destruction or assets ready.
- **Q1 receipts:** two clients and UI submitting the same next ID produce one admitted command; identical retry returns its receipt, changed payload conflicts, stale/expired/future IDs refuse. Eight queued requests remain FIFO, ninth refuses, no overwrite. Every admitted ID receives one terminal receipt or explicit indeterminate state.
- **Q2 mutation fence:** legacy menu/pipe/self-test versus training start/exit races invoke at most one owned native operation. Online/unknown state between submission and consumption refuses before issue. Exception or unreadable post-call queue never causes automatic retry. Wrong queue start reports accepted_wrong_start and retains cleanup ownership.
- **P1 native candidate:** eligible cleared R1CBC only, exact queue mission/start/mode, load observed, stable target mission/position, expected create-entry and new fight start; v4 arena-first claim additionally requires first landing in the actual box and zero warps. Save uncleared on current journey is refused with no mission call.
- **P2 runtime retry/restart/exit:** three native deaths/retries, menu retry, tracked restart, tracked exit, abort before issue and too-late cancellation; slow load and paused intro; no duplicate call storm, stale actor dereference or second warp during intro. Completion waits for observable predicates. Verify restore then ordinary shrine replay/Continue behavior; Return timeout does not count as exited.
- **P3 ownership/persistence:** game rewrites/replaces a start record, failed restore and online/title transitions: no foreign/stale write, unresolved cleanup blocks another mutation. Capture-before-intro remains correct. Compare save effects before/after death, completion and exit under the approved test protocol; label ordinary replay effects honestly. Camera/navmesh/AI checks and Proton check remain required before broad release.

The observer is implementable now using existing sites and scalar hooks. Native practice awaits integration/runtime gates. Arbitrary enemy summoning, in-place boss reset, callable despawn and a reward-free training sandbox remain unsupported capabilities, not hidden options.
