## Async compute
Two compute queues: Q1 (0.53 ms: a 10-dispatch burst at 0.58–0.75 ms and the 358 µs volumetric froxel
dispatch at 6.36 ms) and Q2 (one 0.5 µs dispatch). All of it overlaps GFX work; **none of it fills
the GFX idle gaps**. The 255 µs GFX gap at 6.03–6.28 ms ends 75 µs before Q1's volumetric CB starts,
i.e. the gaps look like submission/fence waits, not "work moved to async".

## GPU idle bubbles
~0.99 ms of the 10.64 ms the GFX queue has no command buffer executing. The two big ones (275 µs, 255 µs)
are between command-buffer submissions → either the render thread submitting late (CPU-bound
submission) or GFX waiting for a fence from another queue/copy. The QueueEvent chunk (CPU submit
timestamps) can disambiguate; not yet decoded.

## FSR4 cost
Segments 389–404 (8.98–9.81 ms): a 30x17 prep dispatch, two 40x720 wave32 WMMA passes (188 + 217 µs)
and a 12-dispatch multi-resolution chain (80x90 → 10x180 groups) plus a 160x90 output pass.
**≈0.81 ms per frame** at 2560x1440 output. All FSR4 shaders are wave32 with `v_wmma` (the game's own
shaders are all wave64, which is how they were told apart).

## ISA notes for the top expensive pipelines
1. **e6429cd12f46fbbb — min/max depth reduction (655 µs/frame over 3 calls).** 64x64 groups, each
   thread loops over a footprint doing `image_sample_lz` (1 channel) → `s_wait_samplecnt 0` →
   `v_min/v_max`, one texel per iteration, then one `image_store`. Fully latency-bound, no LDS, no
   gather4, no wave reduction. Typical use: depth bounds for SDSM shadow cascades or Hi-Z for culling.
   A single-pass gather4 + LDS/wave-reduction version (FidelityFX SPD style) would run in ~20–50 µs.
2. **3e7955a89ee71e82 (366 µs) / 54e610d3e22205ee (218 µs) — 2048² full-screen passes** sampling a depth
   texture and a 2D-array (shadow cascades) in a serial loop / writing 4 MRTs: shadow-map filtering or
   conversion (e.g. EVSM/moments). Scales with shadow resolution → SHADOW quality setting.
3. **5a14b619e553032c (258 + 60 µs) and d32d17ac1b4fa108 (303 + 66 µs)** — huge compute shaders
   (24.7k / 12.4k instructions, 120/118 VGPRs → low occupancy) at half render res, hundreds of
   texture-array taps with serialized waits: screen-space ray-march (SSR/SSGI/AO). → SSR / AO / GI settings
   and REN_RAT.
4. **5123196aa098e19f (358 µs async)** — 3D froxel grid (20x12x12 groups), cube + cascade shadow compares,
   writes 3D textures: volumetric lighting. Hidden behind GFX work today.
5. **bc8a53cc288203cf / 2156f246311e214c** — FSR4 ML network (WMMA).
6. Copies/blurs on ~3×1440p layers (5e9935b5b593a907 173 µs, c570890a613019cc 240 µs) are pure bandwidth.

## Recommendations

### Settings to try first (cheap A/B, re-capture to confirm the pass mapping)
1. **Shadows HIGH → MEDIUM**: should hit the 2048² filter/convert passes (~0.7 ms) and possibly the
   depth reduction. Biggest single expected win.
2. **SSR and AO/GI HIGH → MEDIUM**: the half-res ray-march compute (~0.7–0.9 ms) + blur.
3. **REN_RAT 75 → 67**: G-buffer (1.63 ms) and every render-res pass scale with pixels; FSR4 (0.81 ms)
   does not. Roughly −0.6 ms.
4. Volumetrics: low priority — it runs on async compute and overlaps.
5. FSR4 costs 0.81 ms at 1440p. If the frame stays GPU-bound, FSR 3.1 / XeSS DP4a via OptiScaler is
   cheaper (lower quality); FSR4 Performance/Balanced mode lowers the render-res passes instead.

Method to confirm: capture again at the same spot with one setting lowered, run `rgp_report.py`, and
diff `segments.csv`/`passes.csv` by PSO hash. That maps each setting to its passes.

### Engine-level (needs D3D12 hooking / shader replacement)
1. **Replace the min/max reduction CS (e6429cd12f46fbbb)** with a gather4 + wave-reduction version:
   about **−0.6 ms** on its own. Hook `CreateComputePipelineState` and swap the DXIL by hash.
2. **Barrier storm:** 1369 barriers, 269 segments under 5 µs, 1.16 ms of back-to-back barrier
   (flush/EOP) tails, chains like 80 serialized 1x1x1 dispatches. Merge consecutive `ResourceBarrier`
   calls, drop redundant UAV barriers between independent dispatches, and avoid full CB/DB
   flush + EOP waits when the next pass doesn't read the RT. Potential **0.5–1.0 ms**.
3. **GPU idle bubbles (~1 ms):** find out why GFX starves at 0.1–0.4 ms and 6.0–6.3 ms (late
   ExecuteCommandLists on the CPU side vs cross-queue wait). If it's a CPU submit, submit earlier
   or in more pieces. Moving independent work into the 6.0 ms gap would also help.
4. Fat full-screen copies on 3 × 1440p layers (~0.4 ms): narrower formats or skip the copy.
5. Async: the half-res screen-space compute (5a14…, d32d…) could overlap the shadow / G-buffer work on
   the async queue the game already uses.

Expected total if 1–3 land: ~1.5–2.5 ms → close to the 8.3 ms needed for 120 fps at current settings.

## Caveats
- Single frame, single scene (idle at a shrine). Repeat in a heavier scene (combat, foliage) before
  committing to changes.
- Peak clocks are forced during capture, so absolute times are slightly optimistic vs normal gameplay.
- Segment times are exact GPU time between drains. Splitting a segment between several draws (e.g. the
  80-event G-buffer segment) is approximate.
- api 30/31 are unidentified DX12 event types that always come in pairs with the same PSO
  (probably ExecuteIndirect plus its inner indirect draw). Their VS uses buffer vertex pulling;
  these are not mesh shaders.
